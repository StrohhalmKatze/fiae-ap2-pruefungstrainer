WZ-01 · Versionsverwaltung (Git)

Aufgabe WZ-01.1 · 5 Punkte

a) Zentral vs. verteilt (2 P)

Bei einer zentralen Versionsverwaltung (z. B. Subversion) gibt es nur ein Repository mit der gesamten Historie auf einem Server. Die Entwickler haben lediglich eine Arbeitskopie; Commits, Historie und Vergleiche erfordern eine Verbindung zum Server. Bei einer verteilten Versionsverwaltung (z. B. Git) besitzt jeder Entwickler einen vollständigen Klon des Repositorys einschließlich Historie. Commits erfolgen lokal (auch offline); Änderungen werden per push/pull mit anderen Repositories, meist einem gemeinsamen Remote-Repository, ausgetauscht.

b) Begriffe (3 P)

BegriffErläuterung (Beispiel)
RepositoryDatenbank/Ablage eines Projekts mit allen Dateien und ihrer vollständigen Versionshistorie (lokal im Ordner .git oder als Remote-Repository auf dem GitLab-Server).
CommitGespeicherter Stand (Schnappschuss) der vorgemerkten Änderungen mit eindeutiger ID, Autor, Zeitpunkt, Nachricht und Verweis auf den Vorgänger.
BranchEigenständiger Entwicklungszweig, technisch ein beweglicher Zeiger auf den letzten Commit; ermöglicht paralleles Arbeiten, ohne den Hauptzweig zu verändern.
MergeZusammenführen der Änderungen eines Branches in einen anderen (Fast-Forward oder Merge-Commit; ggf. mit Konfliktauflösung).
PushÜbertragen lokaler Commits in ein entferntes Repository (Remote), damit andere sie erhalten.
TagFester, unveränderlicher Name für einen bestimmten Commit, meist zur Kennzeichnung eines Releases (z. B. v1.3.0).
Bewertung: a) je Variante mit Kernmerkmal (Repository nur auf dem Server vs. vollständige Kopie bei jedem Entwickler) 1 P. b) je richtig erläutertem Begriff 0,5 P.

a) Commit-Graph nach Befehl (10) (4 P)

Die Reihenfolge von N gegenüber F1/F2 auf der Zeitachse ist beliebig (N entstand parallel). origin/main steht nach Befehl (9) ebenfalls auf M; die Angabe ist optional.

b) Fast-Forward? (2 P)

  • Befehl (6) git pull: ja, Fast-Forward. Der lokale main hat seit C keine eigenen Commits; auf origin/main folgt nur N auf C. Git schiebt den Zeiger main einfach von C auf N vor – es entsteht kein neuer Commit.
  • Befehl (7) git merge: kein Fast-Forward. Seit C haben sich beide Zweige weiterentwickelt: main um N, der Feature-Branch um F1 und F2. Git muss die Änderungen zusammenführen und erzeugt den Merge-Commit M mit den zwei Vorgängern N und F2.

a) Stellungnahme zu Punkt 1 (4 P)

Ich stimme der Umstellung auf Git zu. Begründung (zwei der folgenden Argumente):

  • Paralleles Arbeiten ohne Datenverlust: Jeder arbeitet in seinem eigenen Repository bzw. Branch; Änderungen werden per Merge zusammengeführt, und wenn zwei Personen dieselbe Stelle ändern, meldet Git einen Konflikt, statt still zu überschreiben. Der Vorfall aus Anlage 2 (Lukas überschreibt Sarahs Änderungen am AuftragService) wäre so nicht passiert. Tagesordner auf dem Netzlaufwerk verhindern das nicht, sie erzeugen nur weitere Kopien.

c) Branching-Strategie (4 P)

Feature-Branch-Workflow mit Merge Requests (GitLab-Flow). Ablauf für ein Ticket, z. B. MP-142:

  1. Aktuellen Stand holen: git switch main, git pull.
  2. Branch anlegen: git switch -c feature/MP-142-materialliste.
  3. In kleinen Schritten committen (aussagekräftige Nachrichten mit Ticketnummer) und den Branch regelmäßig pushen.
  4. Merge Request nach main öffnen → Pipeline läuft automatisch (Build, Tests, Analyse).
  5. Code-Review durch eine Kollegin/einen Kollegen, Anmerkungen einarbeiten.
  6. Bei grüner Pipeline und Freigabe: Merge in den geschützten main, Feature-Branch löschen; das Deployment erfolgt über die Pipeline.

Begründung: Für ein Team von acht Personen, das ein SaaS-Produkt mit nur einer aktuellen Version kontinuierlich ausliefert, ist dieser Workflow einfach und passt zur Pipeline. Git-Flow (develop/release/hotfix-Branches) wäre unnötig aufwendig. Trunk-based Development mit sehr kurzlebigen Branches ist ebenfalls vertretbar, setzt aber sehr gute Testabdeckung voraus.

WZ-02 · CI/CD & Deployment

Aufgabe WZ-02.1 · 5 Punkte

a) Abgrenzung (3 P)

  • Continuous Integration: Die Entwickler führen ihre Änderungen häufig (mindestens täglich) in den gemeinsamen Hauptzweig zusammen; jede Integration wird automatisch gebaut und getestet, sodass Fehler sofort auffallen.
  • Continuous Delivery: Zusätzlich wird jede erfolgreich geprüfte Version automatisch zu einem auslieferbaren Artefakt verpackt und in Test-/Staging-Umgebungen bereitgestellt. Die Software ist jederzeit releasefähig; die Übernahme in die Produktion erfolgt nach einer manuellen Freigabe.
  • Continuous Deployment: Auch die Produktivsetzung erfolgt automatisch ohne manuelle Freigabe, sobald alle Prüfungen bestanden sind.

b) Aufgaben eines Build-Werkzeugs (2 P)

Zwei davon: Abhängigkeiten (inkl. transitiver) auflösen und herunterladen · Quellcode kompilieren · automatische Tests ausführen · Artefakte packen (JAR/WAR) · Versionen in ein Repository veröffentlichen · Dokumentation/Berichte erzeugen · einheitlicher, reproduzierbarer Build-Ablauf (Lebenszyklus) auf jedem Rechner und dem CI-Server.

Bewertung: a) je Begriff 1 P; der entscheidende Unterschied Delivery/Deployment (manuelle Freigabe ja/nein) muss erkennbar sein. b) je Aufgabe 1 P.

a) Ablauf der Pipeline für einen Push auf main (4 P)

Es handelt sich um Continuous Delivery: Bis zur Staging-Umgebung läuft alles automatisch, der Job deploy-production hat aber when: manual und startet erst, wenn eine berechtigte Person ihn auslöst. Bei Continuous Deployment würde auch die Produktion ohne manuellen Schritt aktualisiert.

Es laufen nur build, unit-tests, integration-tests und code-analyse; package, deploy-staging und deploy-production sind per rules auf main beschränkt. Sie muss den Fehler beheben und erneut pushen; ein Merge in main sollte bei roter Pipeline gesperrt sein.

d) Container (3 P)

Das Container-Image enthält die Anwendung zusammen mit ihrer Laufzeitumgebung (Java 21) und allen Bibliotheken. a) Unterschied (2 P)

Ein Compiler übersetzt den gesamten Quellcode vor der Ausführung in Maschinencode und erzeugt eine ausführbare Datei, die anschließend ohne Compiler ausgeführt wird. a) Java vom Entwicklerrechner bis zum Linux-Server (4 P)

  1. Auf dem Windows-Rechner bzw. in der Pipeline übersetzt der Compiler javac (über Maven) die .java-Dateien in Bytecode (.class-Dateien) – plattformunabhängigen Zwischencode für eine gedachte Maschine, nicht für einen konkreten Prozessor. Die Klassen werden zu einer JAR-Datei bzw. einem Container-Image gepackt.
  2. Dieselbe JAR-Datei wird ohne erneute Übersetzung auf den Linux-Server gebracht.
  3. Dort lädt die Java Virtual Machine (Eclipse Temurin 21 für Linux) den Bytecode, prüft ihn und führt ihn zunächst interpretierend aus.
  4. Der JIT-Compiler erkennt häufig ausgeführte Methoden („Hotspots“) und übersetzt sie zur Laufzeit in optimierten Maschinencode für den Prozessor des Servers – dadurch läuft der Server fast so schnell wie ein direkt kompiliertes Programm.

Die Plattformunabhängigkeit („Write once, run anywhere“) entsteht, weil es für jedes Betriebssystem eine eigene JVM gibt, die denselben Bytecode ausführt.

b) Python oder C++ für die Datenübernahme (4 P)

Python (interpretiert): sehr kurzer, gut lesbarer Code; CSV-Verarbeitung mit der Standardbibliothek; schneller Test-Zyklus ohne Übersetzen – Formatprobleme in den Altdaten lassen sich schnell anpassen und der Import erneut starten. Nachteil: langsamere Ausführung, Typfehler erst zur Laufzeit.
C++ (kompiliert): deutlich schnellere Ausführung, aber höherer Entwicklungsaufwand (Speicherverwaltung, CSV-Parsing, Datenbankanbindung), längerer Entwicklungszyklus, im Team (Java/Kotlin/TypeScript) kaum Erfahrung.
Einsatzzweck: Der Import läuft einmal, mit nur ca. 60 000 Datensätzen (bei Python im Bereich von Sekunden bis Minuten) und unkritischer Laufzeit über Nacht. Der Geschwindigkeitsvorteil von C++ bringt hier nichts, die Entwicklungszeit zählt.
Empfehlung: Python (alternativ Java als Teamsprache) – geringer Aufwand, schnelle Anpassung an fehlerhafte Altdaten.

c) TypeScript und tsc (3 P)

tsc ist ein Transpiler (Source-to-Source-Compiler): Er übersetzt den TypeScript-Code vor der Auslieferung in JavaScript, denn Browser können nur JavaScript ausführen. Dabei prüft er die statischen Typangaben (z. B. auftragNr: number, Struktur der Daten aus der REST-API) und meldet Typfehler, Tippfehler in Eigenschaftsnamen oder fehlende Parameter bereits beim Übersetzen; im erzeugten JavaScript sind die Typen entfernt. Ausgeführt wird das JavaScript dann im Browser (Interpreter + JIT der JavaScript-Engine).
Vorteil: Viele Fehler fallen vor der Ausführung auf statt erst bei den Disponenten; zudem bessere IDE-Unterstützung (Autovervollständigung, sicheres Umbenennen) und eine selbstdokumentierende Schnittstelle zur REST-API.

d) Go-Programm mp-export (5 P)

da) (3 P) Der Go-Compiler (go build) prüft Syntax und Typen und übersetzt die Quelldateien des Programms und der verwendeten Pakete in Maschinencode (Objektcode) für die Zielplattform (hier Windows, x86-64). Der Linker fügt diesen Objektcode mit dem Code der benötigten Bibliotheken (Go-Standardbibliothek, Fremdpakete) und der Go-Laufzeitumgebung zusammen, löst die Verweise auf Funktionen in anderen Paketen auf und erzeugt die ausführbare Datei mp-export.exe. Go bindet die Bibliotheken in der Regel statisch ein – deshalb ist das Ergebnis eine einzelne Datei, die ohne weitere Installation läuft (Anforderung aus Anlage 8).

db) (2 P) Die ausführbare Datei enthält Maschinencode und ein Dateiformat, die an Betriebssystem und Prozessor gebunden sind: Windows nutzt das PE-Format (.exe) und Windows-Systemaufrufe, Linux das ELF-Format und Linux-Systemaufrufe (ggf. auch eine andere Prozessorarchitektur). Deshalb muss für jede Zielplattform eigens übersetzt und gelinkt werden – bei Go per Cross-Compiling, z. B. GOOS=linux GOARCH=amd64 go build. Anders als bei Java gibt es keine virtuelle Maschine, die plattformneutralen Code ausführt.

Bewertung: a) Bytecode 1 P, JVM/Plattformunabhängigkeit 1 P, Interpretation und JIT 1 P, Gesamtablauf Windows → Linux 1 P. b) Bewertung Python 1 P, Bewertung C++ 1 P, Bezug zum Einsatzzweck (einmalig, Datenmenge, Laufzeit unkritisch) 1 P, begründete Empfehlung 1 P (C++ nur mit überzeugender Begründung). c) Übersetzung TS → JS und Ausführung im Browser 1 P, Typprüfung beim Übersetzen 1 P, Vorteil 1 P. da) Kompilieren in Maschinencode 1 P, Aufgabe des Linkers 1 P, eigenständige Datei (statisches Linken) 1 P. db) Plattformabhängigkeit des Maschinencodes/Formats 1 P, Folge (je Plattform eigener Build) 1 P.

Aufgabe WZ-05.1 · 6 Punkte

a) Bibliothek vs. Framework (2 P)

Eine Klassenbibliothek ist eine Sammlung wiederverwendbarer Klassen und Methoden, die der eigene Code bei Bedarf aufruft; die Ablaufsteuerung bleibt beim eigenen Programm (z. B. TerminKern: MonteurPlus ruft istFeiertag() auf). Ein Framework gibt Struktur und Ablauf der Anwendung vor; der eigene Code wird an vorgesehenen Stellen eingefügt und vom Framework aufgerufen – Inversion of Control (z. B. Spring Boot nimmt HTTP-Anfragen an und ruft die passende Controller-Methode auf).

b) Vor- und Nachteil einer umfangreichen PDF-Bibliothek (4 P)

Vorteil (einer, beschrieben): PDF-Erzeugung ist komplex (Schriften, Seitenumbrüche, Tabellen, Fotos, Unterschrift, ggf. PDF/A für die Archivierung). Eine erprobte Bibliothek spart Entwicklungszeit und Kosten, ist von vielen Nutzern getestet und enthält dadurch weniger Fehler als eine Eigenentwicklung; das Team kann sich auf die Fachlogik der Arbeitsberichte konzentrieren. Fehlerbehebungen und Sicherheitsupdates kommen vom Hersteller.

Nachteil (einer, beschrieben): Abhängigkeit vom Hersteller bzw. Projekt – wird die Bibliothek nicht mehr gepflegt oder ändert sich die Lizenz, muss man sie mit großem Aufwand ersetzen. Weitere: Lizenzbedingungen und -kosten (PdfMaker Core: AGPL oder 2 400 € pro Jahr, Anlage 11), Einarbeitungsaufwand in eine umfangreiche API, größere Anwendung, obwohl nur ein Bruchteil genutzt wird, Sicherheitslücken im fremden Code.

Bewertung: a) Bibliothek 1 P, Framework mit Steuerungsumkehr 1 P. b) Vorteil 2 P, Nachteil 2 P (jeweils 1 P für das Stichwort, 1 P für die Beschreibung mit Begründung bzw. Bezug zur Situation).

a) Aufgaben von Maven bei Abhängigkeiten (3 P)

In der pom.xml werden nur die direkten Abhängigkeiten mit ihren Koordinaten (groupId, artifactId, version) deklariert. WZ-06 · Open Source & Lizenzen

Aufgabe WZ-06.1 · 6 Punkte

a) Open Source (3 P)

Open-Source-Software ist Software, deren Quellcode öffentlich zugänglich ist und deren Lizenz jedem erlaubt, die Software für beliebige Zwecke (auch kommerziell) zu nutzen, zu untersuchen, zu verändern und – verändert oder unverändert – weiterzugeben. Welche Bedingungen dabei gelten (z. B. Lizenzhinweise beilegen, Änderungen offenlegen), legt die jeweilige Lizenz fest; anerkannte Open-Source-Lizenzen erfüllen die Open Source Definition der OSI (z. B. MIT, Apache 2.0, GPL). Das Urheberrecht bleibt beim Autor; meist ist die Nutzung kostenlos.

b) Einsatz ohne Einschränkung? (2 P)

Nein. Open Source bedeutet nicht „rechtefrei“: Man darf eine Bibliothek nur unter den Bedingungen ihrer Lizenz einsetzen. Copyleft-Lizenzen wie die GPL verlangen z. B., dass ein Programm, das die Bibliothek enthält, bei Weitergabe ebenfalls unter der GPL mit vollständigem Quellcode weitergegeben wird – das widerspricht dem proprietären Modell von MonteurPlus. Auch permissive Lizenzen verlangen zumindest Lizenz- und Copyright-Hinweise.

c) Beispiele (1 P)

Permissiv: MIT, BSD, Apache 2.0. Copyleft: GPL, AGPL, LGPL (schwach), MPL 2.0 (schwach), EPL 2.0 (schwach).

Bewertung: a) offener Quellcode 1 P, Nutzungs-/Änderungs-/Weitergaberechte 1 P, Bedingungen durch die Lizenz 1 P. b) „Nein“ mit Verweis auf Lizenzbedingungen 1 P, Beispiel/Begründung (z. B. Copyleft) 1 P. c) je Beispiel 0,5 P.

b) Vor- und Nachteile von Open-Source-Bibliotheken (4 P)

Vorteile (zwei): keine Lizenzkosten – wichtig, weil bei wachsender Kundenzahl keine Gebühren je Nutzer anfallen · Quellcode einsehbar: Qualität und Sicherheit prüfbar, Fehler selbst analysieren und notfalls beheben · große Community, weite Verbreitung, viel Wissen und schnelle Fehlerbehebung bei aktiven Projekten · keine Abhängigkeit von einem Hersteller, bei Einstellung kann das Projekt weitergeführt (geforkt) werden.

Nachteile (zwei): Lizenzpflichten müssen geprüft und eingehalten werden; Copyleft (Nr. 4, 5) kann das Geschäftsmodell gefährden → Aufwand für Lizenz-Compliance · keine Gewährleistung und kein garantierter Support (Haftungsausschluss) – gegenüber Albers haftet Lindner Digital trotzdem selbst · Fortbestand unsicher (Projekt wird eingestellt oder Lizenz geändert) · Sicherheitslücken sind öffentlich sichtbar, Updates muss man selbst verfolgen (vgl. json-mini).

Fazit für die Geschäftsführung: Open Source ja, aber mit festem Prüfprozess (Lizenz, Pflegezustand, Sicherheit) vor jedem Einsatz.

c) GPL-Code in eine MIT-Bibliothek kopieren (3 P)

Nicht zulässig. Der kopierte SignPad-Code bleibt urheberrechtlich geschützt und steht unter der GPL-3.0. Wird er in lindner-utils übernommen, entsteht ein abgeleitetes Werk, das bei der Veröffentlichung insgesamt unter der GPL-3.0 stehen muss. Eine Veröffentlichung unter MIT würde die GPL verletzen, weil MIT u. a. erlaubt, den Code in proprietäre Software einzubauen – GPL-Code lässt sich nicht in eine permissive Lizenz „umlizenzieren“ (umgekehrt wäre MIT-Code in einem GPL-Projekt zulässig). Außerdem würde lindner-utils selbst copyleft-pflichtig und wäre in MonteurPlus nicht mehr einsetzbar. Lösung: die Funktionen ohne Kopie selbst neu entwickeln, eine Bibliothek mit permissiver Lizenz nutzen oder den Rechteinhaber von SignPad um eine Lizenz unter MIT bitten (nur er kann umlizenzieren).

d) SBOM (3 P)

Eine Software Bill of Materials ist eine maschinenlesbare, vollständige „Stückliste“ aller Komponenten eines Softwareprodukts – einschließlich der transitiven Abhängigkeiten – mit Name, Version, Herkunft, Lizenz und Prüfsumme (Formate SPDX oder CycloneDX). Sie wird in der Pipeline automatisch für jede Version erzeugt (z. B. per Maven-Plugin).

Nutzen am Beispiel: FeiertageDE und json-mini stehen nicht in der pom.xml, sondern kommen über TerminKern ins Produkt. Die SBOM führt sie trotzdem auf. Als die Denial-of-Service-Lücke in json-mini 0.9.2 bekannt wurde, hätte ein Abgleich der SBOM mit Schwachstellendatenbanken sofort gezeigt, dass Server-Version 1.3.0 betroffen ist (Schwachstellenmanagement). Außerdem lassen sich ihre Lizenzen (BSD-3-Clause, MIT) für Lizenzprüfung und Lizenzhinweise gegenüber den SaaS-Kunden erfassen. Der EU Cyber Resilience Act verlangt von Herstellern künftig eine SBOM.
