a) Zweck der DTD (2 P)

Die DTD legt verbindlich fest, wie ein Wochenangebot aufgebaut sein muss: welche Elemente und Attribute erlaubt sind, in welcher Reihenfolge und Anzahl sie vorkommen und welche Angaben Pflicht sind. Sie ist damit die gemeinsame Schnittstellenvereinbarung zwischen den 28 Erzeugerbetrieben und dem KistenPortal. Mit ihr kann jede hochgeladene Datei vor dem Import automatisch validiert werden; fehlerhafte Dateien werden mit einer Meldung abgewiesen, statt falsche Daten zu importieren.

c) Gültig, aber unsinnig (4 P)

Warum die Prüfung bestanden wird: In der DTD sind menge und preis als (#PCDATA) deklariert, also als beliebiger Text. Eine DTD kennt keine Datentypen und keine Wertebereiche; sie prüft nur, ob die Elemente vorhanden sind und in der richtigen Reihenfolge stehen. „ca. 80“ und „-1.90“ sind Text und damit zulässig.

Maßnahmen (zwei davon):

  • XML-Schema statt DTD mit Datentypen und Einschränkungen, z. B. menge als positive ganze Zahl und preis als Dezimalzahl größer 0 (Auszug unten, getestet: die KW-47-Datei wird abgewiesen).

a) Objekt und Array (2 P)

Ein Objekt steht in geschweiften Klammern { } und ist eine ungeordnete Menge von Schlüssel-Wert-Paaren; auf einen Wert greift man über seinen Namen (Schlüssel, immer ein String) zu, z. B. eine Kiste mit "kisteId" und "preis". Ein Array steht in eckigen Klammern [ ] und ist eine geordnete Liste von Werten ohne Schlüssel; auf einen Wert greift man über seine Position (Index) zu, z. B. eine Liste mehrerer Kisten.

Java · Aufgabe_SD_02_3.java (Auszug)

static String offeneStoppsAlsJson(List<Stopp> stopps) {
    String json = "[";
    boolean erster = true;
    for (int i = 0; i < stopps.size(); i++) {
        Stopp s = stopps.get(i);
        if (!s.isZugestellt()) {
            if (!erster) {
                json = json + ", ";                  // Trennzeichen nur ZWISCHEN Objekten
            }
            json = json + "{\"position\": " + s.getPosition()
                    + ", \"kundenNr\": " + s.getKundenNr()
                    + ", \"ort\": \"" + s.getOrt() + "\""   // Zeichenkette in Anführungszeichen
                    + ", \"kisten\": " + s.getAnzahlKisten() + "}";
            erster = false;
        }
    }
    json = json + "]";
    return json;
}

Aufgabe SD-03.3 · 18 Punkte

a) Konzept einer REST-API (3 P)

Eine REST-API stellt die Daten des KistenPortals als Ressourcen bereit (Kisten, Kunden, Abos …), die jeweils über eine eindeutige URI adressiert werden. Clients greifen über die Standardmethoden von HTTP darauf zu (GET lesen, POST anlegen, PUT/PATCH ändern, DELETE löschen) und tauschen Repräsentationen der Ressourcen aus, meist im JSON-Format. Die Kommunikation ist zustandslos: Jede Anfrage enthält alle nötigen Informationen, der Server speichert keine Sitzung. Client und Server sind dadurch lose gekoppelt, sodass App, Webshop und Partner dieselbe Schnittstelle nutzen können.

b) Sicher und idempotent (5 P)

RequestsicheridempotentBegründung
GET /v1/kisten?bio=truejajaliest nur, ändert nichts auf dem Server

DELETE …/lieferadressen/2neinjanach dem ersten Aufruf ist die Adresse gelöscht; weitere Aufrufe ändern den Zustand nicht (Antwort ggf. 404)

c) Doppeltes Abo (4 P)

Ursache: „Abo abschließen“ sendet einen POST-Request, und POST ist nicht idempotent. Der erste Request ist beim Server angekommen und hat das Abo angelegt, nur die Antwort (201) ging bei der schlechten Verbindung verloren. Das erneute Tippen sendet einen zweiten POST, der ein zweites, identisches Abo anlegt.

Lösung: Die App erzeugt für jeden Bestellvorgang einen eindeutigen Idempotenzschlüssel (z. B. eine UUID) und sendet ihn in einem Header (z. B. Idempotency-Key) mit. Der Server merkt sich bereits verarbeitete Schlüssel und liefert bei einer Wiederholung die ursprüngliche Antwort zurück, statt ein neues Abo anzulegen. Weitere mögliche Lösungen: Die App vergibt die Abo-ID selbst und legt das Abo mit PUT /kunden/10427/abos/{uuid} an (idempotent); der Server prüft auf Dubletten (gleiche Kundin, gleiche Kiste innerhalb kurzer Zeit) und antwortet mit 409.

e) REST und SOAP (2 P)

  • REST ist ein Architekturstil, SOAP ein festgelegtes Protokoll.
  • REST erlaubt beliebige Formate (meist JSON), SOAP nutzt ausschließlich XML (SOAP-Envelope).
  • REST verwendet die HTTP-Methoden auf Ressourcen-URIs; bei SOAP steht die Operation im XML-Body, meist per POST an einen einzigen Endpunkt.
  • SOAP-Dienste werden verbindlich per WSDL beschrieben, bei REST ist eine Beschreibung (z. B. OpenAPI) optional.
Bewertung: a) je fachlich richtig erläutertem Aspekt 1 P, höchstens 3 P (Ressourcen/URI, HTTP-Methoden, Repräsentationen/JSON, zustandslos, lose Kopplung). b) je Zeile 1 P (beide Einträge richtig 0,5 P, Begründung 0,5 P); bei PATCH wird auch „nein“ mit Hinweis auf die allgemeine Nicht-Idempotenz voll bewertet. c) Ursache 2 P (POST nicht idempotent 1 P, Antwort verloren/zweiter Request 1 P), Lösung 2 P; „Button nach dem Tippen sperren“ allein 1 P, weil automatische Wiederholungen dadurch nicht verhindert werden. d) je Request 2 P (Request-Zeile mit richtiger Methode und URI 1 P, Body 1 P); beim PUT muss die vollständige Repräsentation gesendet werden, beim PATCH genügt der geänderte Wert. e) je Unterschied 1 P.

Erklärung: b) prüft Verständnis statt Auswendiglernen: Ob ein PATCH idempotent ist, hängt von der konkreten Änderung ab. Das Setzen fester Werte ist idempotent, „erhöhe um 1“ wäre es nicht. Der Body des PUT in d) wurde gegen die Repräsentation aus Anlage 2 geprüft (alle acht Felder, nur der Liefertag ist geändert).

Aufgabe SD-05.1 · 6 Punkte

a) Hauptziel (2 P)

Das Hauptziel einer eRechnung ist die automatische, elektronische Verarbeitung beim Empfänger: Die Rechnungsdaten liegen strukturiert (als XML) vor und können ohne Abtippen direkt in Buchhaltung bzw. ERP-System übernommen, geprüft und gebucht werden. Das spart Zeit und Kosten und vermeidet Erfassungsfehler. Eine für Menschen lesbare Darstellung ist dabei zweitrangig.

b) eRechnung oder nicht? (4 P)

Nr.eRechnung?Begründung

Aufgabe SD-05.2 · 10 Punkte

a) Empfangen und ausstellen (3 P)

  • Empfangen: Seit dem 1. Januar 2025 müssen alle Unternehmen in Deutschland eRechnungen von anderen Unternehmen empfangen können.
  • Ausstellen – Übergangszeit: Bis Ende 2026 dürfen Unternehmen noch Papierrechnungen oder andere elektronische Formate wie PDF versenden (PDF nur mit Zustimmung des Empfängers). Im Jahr 2027 gilt das nur noch für Unternehmen, deren Gesamtumsatz im Vorjahr höchstens 800.000 € betrug.
  • Ausstellen – Pflicht: Ab dem 1. Januar 2028 müssen alle Unternehmen eRechnungen ausstellen (ausgenommen Rechnungen bis 250 € und Fahrausweise).

b) XRechnung und ZUGFeRD (4 P)

XRechnung ist ein rein XML-basiertes Format: Die Rechnung besteht nur aus strukturierten Daten für die Software (Datenaspekt). Ein Mensch kann sie nur mit einem Anzeigeprogramm (Viewer) lesen. Viele Behörden verlangen XRechnung und nutzen die Leitweg-ID, um die Rechnung an die zuständige Stelle weiterzuleiten.

ZUGFeRD ist ein hybrides Format: ein PDF/A-3-Dokument, das ein Mensch direkt lesen kann, mit einer eingebetteten XML-Datei, die die Software verarbeitet. Es vereint also visuellen und Datenaspekt. Weichen beide Teile voneinander ab, gelten die XML-Daten.

c) PDF-Rechnungen im Jahr 2027 (3 P)

Geschäftskunden (B2B): Nicht mehr zulässig. Die FrischeKiste erwartet für 2026 einen Umsatz von rund 4,6 Mio. € und liegt damit deutlich über 800.000 €. Die Übergangsregel für 2027 gilt daher nicht; ab dem 1. Januar 2027 müssen Rechnungen an Geschäftskunden als eRechnung ausgestellt werden (ausgenommen Kleinbetragsrechnungen bis 250 €).

Privatkunden (B2C): weiterhin zulässig, denn Rechnungen an Privatkunden sind von der Pflicht nicht betroffen.

Bewertung: a) Empfang ab 2025 1 P, Übergang 2025/2026 und 2027 mit 800.000-€-Grenze 1 P, Pflicht ab 2028 1 P. b) je Format 2 P (Aufbau 1 P, Folge für Mensch bzw. Software 1 P). c) Geschäftskunden mit Begründung über den Umsatz 2 P, Privatkunden 1 P. Antworten in englischer Sprache oder wörtliche Übersetzungen ohne eigene Formulierung erhalten Abzüge.

Erklärung: c) verlangt, den Text auf die Situation anzuwenden: Entscheidend ist der Umsatz des Vorjahres (2026) – diese Angabe steht in Anlage 1, nicht im Text.

b) Online-Prüfseite (4 P)

  • Datenschutz und Geheimhaltung: Echte Rechnungen enthalten personenbezogene Daten (Namen, Anschriften, ggf. Bankverbindung) und Geschäftsdaten (Preise, Mengen, Kunden). Das Hochladen auf eine fremde Website ist eine Übermittlung an Dritte, für die es keine Rechtsgrundlage gibt (DSGVO). Deshalb nur Test- oder anonymisierte Rechnungen hochladen.
  • Vertrauenswürdigkeit und Aussagekraft: Den Anbieter prüfen (Impressum, Serverstandort, Datenschutzerklärung, Speicherdauer). Das Ergebnis kann falsch, unvollständig oder veraltet sein (z. B. nur XSD statt Schematron, alte XRechnung-Version); es ersetzt keine Prüfung mit dem offiziellen Validator. Besser den KoSIT-Validator lokal betreiben.

c) Warum die Schema-Validierung nicht reicht (6 P)

ZeileFehler
5Das Fälligkeitsdatum (16.11.2026) liegt vor dem Rechnungsdatum (30.11.2026).
25 (29)Der Nettobetrag der Position 2 ist falsch: 4 × 27,90 € = 111,60 €, angegeben sind 101,60 €. Dadurch stimmt auch die Summe der Positionen (148,00 € + 101,60 € = 249,60 €) nicht mit dem Nettogesamtbetrag von 259,60 € (Zeile 29) überein.
31Der Bruttogesamtbetrag ist falsch: 259,60 € + 18,17 € = 277,77 €, angegeben sind 278,77 €.

Erläuterung: Das XML-Schema prüft nur die Struktur (Elemente, Reihenfolge, Pflichtangaben) und die Datentypen einzelner Werte – hier, dass die Datumsangaben gültige Daten und die Beträge Dezimalzahlen sind. Das ist bei allen Werten der Fall. Logische und rechnerische Zusammenhänge zwischen mehreren Werten (Fälligkeit nach Rechnungsdatum, Menge × Preis = Nettobetrag, Summen) lassen sich mit einer XSD nicht ausdrücken. Dafür sind zusätzlich Geschäftsregeln nötig, z. B. die Schematron-Regeln der EN 16931/XRechnung im Validator sowie Plausibilitätsprüfungen und Tests der eigenen Berechnungslogik.

d) Transportverschlüsselung (3 P)

da) TLS beruht auf einer hybriden Verschlüsselung: asymmetrisch für den sicheren Austausch eines Sitzungsschlüssels, symmetrisch für die schnelle Übertragung der Daten.

db) TLS verschlüsselt nur die jeweilige Teilstrecke (Mailprogramm → Mailserver, Mailserver → Mailserver). Auf jedem beteiligten Mailserver wird die Nachricht entschlüsselt und liegt dort im Klartext vor; Betreiber oder Angreifer mit Zugriff auf einen Server könnten sie lesen oder verändern. Alternative: Ende-zu-Ende-Verschlüsselung der E-Mail mit S/MIME oder PGP – oder die Übermittlung über Peppol bzw. ein Rechnungsportal (HTTPS).

e) Leitweg-ID (2 P)

Die Leitweg-ID ist eine eindeutige Kennung des öffentlichen Rechnungsempfängers (hier der Stadt Heidmoor bzw. der Kita Sonnenblume). Der Auftraggeber teilt sie mit, und sie muss in der XRechnung angegeben werden (Käuferreferenz). Mit ihr wird die Rechnung im Rechnungseingangssystem der Verwaltung automatisch an die zuständige Stelle weitergeleitet und zugeordnet; fehlt sie, wird die Rechnung in der Regel abgelehnt.

Bewertung: a) je Möglichkeit 1 P. b) je Punkt 2 P (Nennung 1 P, Erläuterung mit Begründung 1 P). c) je Fehler mit Zeile und Begründung 2 P (höchstens zwei Fehler werden gewertet), Erläuterung „Schema prüft nur Struktur und Datentypen, keine Zusammenhänge/Geschäftsregeln“ 2 P. d) da) 1 P, db) Begründung 1 P, Alternative 1 P. e) 2 P (Kennung des Empfängers 1 P, Zweck Weiterleitung/Zuordnung 1 P).

Erklärung: c) entspricht W25 T1 A3bc: Dort war der Nettogesamtbetrag aus den Bruttowerten statt aus den Nettowerten gebildet – formal korrekt, fachlich falsch. Genau diese Klasse von Fehlern deckt eine XSD nie ab.
