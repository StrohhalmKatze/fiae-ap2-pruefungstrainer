OOP-01 · Grundkonzepte: Klasse, Objekt, Kapselung

Aufgabe OOP-01.1 · 6 Punkte

a) Klasse und Objekt (2 P)

Die Klasse Paketfach ist der Bauplan (Datentyp): Sie legt fest, welche Attribute (Fachnummer, Größe, Inhalt, Abholcode) und welche Methoden (einlegen, entnehmen, istFrei …) jedes Paketfach hat. Ein Objekt ist ein konkretes Paketfach, das zur Laufzeit mit new erzeugt wird und eigene Attributwerte hat, z. B. Fach 7 der Station Hafenstraße, Größe "M", belegt mit Sendung KT-1001. Für die Station gibt es also eine Klasse, aber 24 Paketfach-Objekte.

Bewertung: 1 P Klasse als Bauplan/Typ mit Attributen und Methoden, 1 P Objekt als konkrete Instanz mit eigenem Zustand; ohne Bezug zum Beispiel höchstens 1 P.

b) Datenkapselung (3 P)

Die Attribute eines Paketfachs (fachNr, groesse, inhalt, abholcode) werden nach außen verborgen (Sichtbarkeit private). Andere Objekte, z. B. die Steuerung der Paketstation, können den Zustand nur über die öffentlichen Methoden lesen oder ändern (getGroesse(), istFrei(), einlegen, entnehmen). Niemand kann von außen direkt inhalt überschreiben oder den Abholcode auslesen.

Vorteile (zwei davon):

  • Gültige Daten: Die Methoden prüfen jede Änderung – eine Sendung kann z. B. nur in ein freies, ausreichend großes Fach gelegt werden.
  • Wartbarkeit: Die interne Darstellung (z. B. Größe als Zahl statt Text) kann geändert werden, ohne dass andere Klassen angepasst werden müssen.
  • Geringe Kopplung: Andere Klassen hängen nur von der öffentlichen Schnittstelle ab.
  • Fehlersuche: Nur die Klasse selbst ändert ihre Attribute; Fehler lassen sich leichter eingrenzen.
Bewertung: 1 P für das Prinzip (private Attribute, Zugriff nur über Methoden), je 1 P pro erläutertem Vorteil (max. 2).

c) Aufgabe eines Konstruktors (1 P)

Der Konstruktor wird beim Erzeugen eines Objekts (new) automatisch aufgerufen und initialisiert das neue Objekt, d. h. er setzt die Anfangswerte der Attribute.

Bewertung: 1 P.

Java · Aufgabe_OOP_01_3.java (Klasse Paketfach)

class Paketfach {
    private static int anzahlFaecher = 0;
    private final int fachNr;
    private final String groesse;
    private Sendung inhalt;
    private String abholcode;

    public Paketfach(int fachNr, String groesse) {
        this.fachNr = fachNr;
        this.groesse = groesse;
        this.inhalt = null;
        this.abholcode = null;
        anzahlFaecher = anzahlFaecher + 1;
    }

    public Paketfach(int fachNr) {
        this(fachNr, "M");
    }

    public static int getAnzahlFaecher() {
        return anzahlFaecher;
    }

    public int getFachNr() {
        return fachNr;
    }

    public String getGroesse() {
        return groesse;
    }

    public boolean istFrei() {
        return inhalt == null;
    }

    public boolean einlegen(Sendung s, String code) {
        if (s != null && istFrei() && rang(s.getGroesse()) <= rang(groesse)) {
            inhalt = s;
            abholcode = code;
            return true;
        }
        return false;
    }

    public Sendung entnehmen(String code) {
        if (!istFrei() && abholcode.equals(code)) {
            Sendung s = inhalt;
            inhalt = null;
            abholcode = null;
            return s;
        }
        return null;
    }

    private int rang(String groesse) {
        if (groesse.equals("S")) {
            return 1;
        } else if (groesse.equals("M")) {
            return 2;
        } else if (groesse.equals("L")) {
            return 3;
        }
        return 0;
    }
}

b) Abstrakte Klasse oder Interface? (3 P)

Entscheidung: Interface Druckbar.

  • Abholschein erbt bereits von Dokument. Java erlaubt nur eine Oberklasse – eine abstrakte Klasse Druckbar könnte Abholschein nicht zusätzlich erweitern. Interfaces kann eine Klasse dagegen beliebig viele implementieren.
  • Die Klassen haben keine gemeinsamen Attribute und keinen gemeinsamen Code; es wird nur eine gemeinsame Fähigkeit („kann gedruckt werden“) vereinbart. Genau dafür ist ein Interface gedacht; eine ist-ein-Beziehung zu einem gemeinsamen Oberbegriff besteht nicht.

Bewertung: 1 P Entscheidung, je 1 P pro stichhaltigem Argument (max. 2). Die Entscheidung für eine abstrakte Klasse ist wegen der bestehenden Vererbung von Abholschein falsch (0 P für die Entscheidung).

class Paket extends Postsendung implements Versicherbar {
    public Paket(String sendungsNr, double gewicht) {
        super(sendungsNr, gewicht);
    }

    @Override
    public double berechnePorto() {
        if (getGewicht() <= 5.0) {
            return 5.49;
        }
        return 8.99;
    }

    @Override
    public double maxGewicht() {
        return 31.5;
    }

    @Override
    public boolean istStationsfaehig() {
        return true;
    }

    @Override

        double betrag = warenwert * 0.01;
        if (betrag < 2.00) {
            betrag = 2.00;
        }
        return betrag;
    }
}

d) Eine Oberklasse, aber mehrere Interfaces (4 P)

Java erlaubt bei Klassen nur Einfachvererbung. Würde eine Klasse von zwei Klassen erben, die beide eine Methode mit gleicher Signatur implementieren oder gleichnamige Attribute haben, wäre nicht eindeutig, welche Implementierung bzw. welches Attribut gilt; erben beide Klassen außerdem von einer gemeinsamen Oberklasse, wären deren Attribute doppelt vorhanden (Diamond-Problem).

Ein Interface enthält dagegen keine Instanzattribute und (in der klassischen Form) nur Methodensignaturen ohne Implementierung. Paket implementiert berechneVersicherung selbst – es gibt genau eine Implementierung und damit keinen Konflikt. Deshalb darf eine Klasse eine Oberklasse haben (Postsendung, „ist ein“) und zusätzlich beliebig viele Interfaces realisieren (Versicherbar, „kann versichert werden“).

Bewertung: 2 P für die Begründung des Verbots (Mehrdeutigkeit/Diamond-Problem), 2 P dafür, warum Interfaces unproblematisch sind (kein Zustand, keine konkurrierende Implementierung).

OOP-03 · Polymorphie, Überladen/Überschreiben, Generics

Aufgabe OOP-03.1 · 6 Punkte

a) Polymorphie (3 P)

Polymorphie (Vielgestaltigkeit) bedeutet, dass eine Variable vom Typ einer Oberklasse oder eines Interfaces auf Objekte verschiedener Unterklassen verweisen kann. Derselbe Methodenaufruf führt je nach Objekt zu unterschiedlichem Verhalten, weil die Unterklassen die Methode überschreiben. Welche Implementierung ausgeführt wird, wird erst zur Laufzeit anhand der tatsächlichen Klasse des Objekts entschieden (dynamische bzw. späte Bindung). Beispiel: Zustellung z := new Expresszustellung() – der Aufruf z.gebuehr() führt die Methode von Expresszustellung aus.

Bewertung: 1 P Oberklassen-Referenz auf Objekte verschiedener Unterklassen, 1 P gleicher Aufruf – unterschiedliches Verhalten durch Überschreiben, 1 P Entscheidung zur Laufzeit/dynamische Bindung. Ohne Bezug zu den Klassen aus Anlage 7 höchstens 2 P. Auch akzeptiert: Hinweis auf statische Polymorphie durch Überladen als Ergänzung.

b) Überladen oder Überschreiben? (3 P)

Nr.ErgebnisBegründung
1Überladengleiche Klasse, gleicher Name, unterschiedliche Parameterliste (integer bzw. string)

class Ablage<T> {
    private String bezeichnung;
    private int kapazitaet;
    private List<T> elemente;

    public Ablage(String bezeichnung, int kapazitaet) {
        this.bezeichnung = bezeichnung;
        this.kapazitaet = kapazitaet;
        this.elemente = new ArrayList<>();
    }

    public boolean ablegen(T element) {
        if (elemente.size() < kapazitaet && !elemente.contains(element)) {
            elemente.add(element);
            return true;
        }
        return false;
    }

    public int anzahl() {
        return elemente.size();
    }

    public List<T> getElemente() {
        return elemente;
    }

    public T maximum(Vergleicher<T> v) {
        if (elemente.size() == 0) {
            return null;
        }
        T max = elemente.get(0);
        for (int i = 1; i < elemente.size(); i++) {
            if (v.vergleiche(elemente.get(i), max) > 0) {
                max = elemente.get(i);
            }
        }
        return max;
    }
}

interface Vergleicher<T> {
    int vergleiche(T a, T b);
}

class Lagerverwaltung {
    public List<Lagerposten> faelligePosten(Ablage<Lagerposten> ablage, Datum heute) {
        List<Lagerposten> ergebnis = new ArrayList<>();
        List<Lagerposten> posten = ablage.getElemente();
        for (int i = 0; i < posten.size(); i++) {
            Lagerposten p = posten.get(i);
            if (p.istFaellig(heute)) {          // dynamische Bindung
                ergebnis.add(p);
            }
        }
        return ergebnis;
    }
}

a) Funktionsweise und Begründung (4 P)

Funktionsweise: Ein Subject (hier Sendungsstatus) verwaltet eine Liste angemeldeter Observer. Interessierte Objekte (KundenApp, Hallenanzeige) melden sich mit addObserver an. Ändert sich der Zustand des Subjects, ruft es notifyObservers() auf; diese Methode ruft bei jedem angemeldeten Observer update() auf, und jeder Observer aktualisiert sich daraufhin selbst.

Begründung: Eine Statusänderung muss sofort und automatisch an mehrere, unterschiedliche Anzeigen weitergegeben werden. Weil das Subject nur das Interface Observer kennt, können später weitere Anzeigen (Kundenportal) ergänzt werden, ohne Sendungsstatus zu ändern – genau das fordert Anlage 12. Anzeigen müssen den Status nicht ständig abfragen (kein Polling).

interface Subject {
    void addObserver(Observer o);
    void removeObserver(Observer o);
    void notifyObservers();
}

interface Observer {
    void update();
}

class Sendungsstatus implements Subject {
    private String sendungsNr;
    private String status;
    private List<Observer> observers;

    public Sendungsstatus(String sendungsNr) {
        this.sendungsNr = sendungsNr;
        this.status = "Angekündigt";
        this.observers = new ArrayList<>();
    }

    public String getSendungsNr() {
        return sendungsNr;
    }

    public String getStatus() {
        return status;
    }

    public void setStatus(String status) {
        this.status = status;
        notifyObservers();
    }

    @Override
    public void addObserver(Observer o) {
        observers.add(o);
    }

    @Override
    public void removeObserver(Observer o) {
        observers.remove(o);
    }

    @Override
    public void notifyObservers() {
        for (int i = 0; i < observers.size(); i++) {
            observers.get(i).update();
        }
    }
}

class KundenApp implements Observer {
    private Sendungsstatus quelle;
    private String letzteMeldung;

    public KundenApp(Sendungsstatus quelle) {
        this.quelle = quelle;
        quelle.addObserver(this);
    }

    @Override
    public void update() {
        letzteMeldung = quelle.getStatus();     // Pull: Daten selbst abholen
        anzeigen();
    }

    public void anzeigen() {
        System.out.println("  KundenApp:       " + letzteMeldung);
    }

    public String getLetzteMeldung() {
        return letzteMeldung;
    }
}

class Hallenanzeige implements Observer {
    private Sendungsstatus quelle;
    private int hallenNr;
    private String zeile;

    public Hallenanzeige(Sendungsstatus quelle, int hallenNr) {
        this.quelle = quelle;
        this.hallenNr = hallenNr;
        quelle.addObserver(this);
    }

    @Override
    public void update() {
        zeile = quelle.getStatus();             // Pull
        anzeigen();
    }

    public void anzeigen() {
        System.out.println("  Hallenanzeige " + hallenNr + ": " + zeile);
    }
}

f) Push-Variante (2 P)

Bei der Push-Variante schickt das Subject die geänderten Daten gleich mit: Die Methode erhält Parameter, z. B. update(sendungsNr : string, status : string), und notifyObservers() ruft observers.get(i).update(sendungsNr, status) auf. Der Observer muss den Status nicht mehr mit getStatus() abholen (der Rückaufruf im Sequenzdiagramm entfällt) und braucht keine Referenz quelle mehr. Nachteil: Alle Observer erhalten alle Daten, und bei zusätzlichen Daten ändert sich die Schnittstelle.

Bewertung: 1 P geänderte Signatur/Daten als Parameter, 1 P Wegfall von getStatus() bzw. der Referenz auf das Subject.

    void update(String sendungsNr, String status);   // Daten werden mitgeschickt
