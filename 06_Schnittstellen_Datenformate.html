SD-01 · XML Kam vor – 2/9 – W25, W22

Vorkommen: 2/9 · Prüfungen: W25, W22 · Teil 1, Aufgabe 3 · Hinweis: eRechnungen (W25) sind XML-Dokumente

Was ist XML? Hintergrund – 0/9

XML (Extensible Markup Language) ist eine textbasierte Auszeichnungssprache für hierarchisch strukturierte Daten. Sie ist für Menschen und Maschinen lesbar, plattform- und programmiersprachenunabhängig und wird vor allem für den Datenaustausch zwischen Systemen verwendet (eRechnung, Behördenstandards, SOAP-Webservices, Konfigurationsdateien, Office-Dateiformate). Anders als HTML gibt XML keine Elementnamen vor („extensible“): Die Namen legt man selbst fest. Welche Elemente in welcher Reihenfolge erlaubt sind, beschreibt eine DTD oder ein XML-Schema (XSD).

Wohlgeformt und gültig Kam vor – 1/9 – W22

Merke Wohlgeformt (well-formed) = das Dokument hält die Syntaxregeln von XML ein. Das prüft jeder XML-Parser, auch ohne DTD.
Gültig (valid) = das Dokument ist wohlgeformt und entspricht zusätzlich einer vorgegebenen Grammatik (DTD oder XSD): nur erlaubte Elemente und Attribute, richtige Reihenfolge und Anzahl, Pflichtangaben vorhanden.
Jedes gültige Dokument ist wohlgeformt – aber nicht umgekehrt.

Regeln der Wohlgeformtheit (Syntax)

  1. genau ein Wurzelelement
  2. zu jedem Start-Tag ein passendes End-Tag (oder leeres Element <x/>)
  3. korrekt verschachtelt: <a><b></b></a>, nicht <a><b></a></b>
  4. Groß-/Kleinschreibung zählt: <Preis> ≠ <preis>
  5. Attributwerte in Anführungszeichen, kein Attributname doppelt im selben Element
  6. < und & im Text nur als Entität
  7. Namen beginnen mit Buchstabe oder _, keine Leerzeichen
  8. XML-Deklaration (falls vorhanden) ganz am Anfang

Zusätzlich für die Gültigkeit (gegen DTD/XSD)

  1. nur deklarierte Elemente und Attribute
  2. Kindelemente in der vorgegebenen Reihenfolge und Anzahl
  3. Pflichtattribute vorhanden, Attributwerte aus der erlaubten Liste
  4. Werte vom Typ ID im ganzen Dokument eindeutig
  5. Wurzelelement wie in der DOCTYPE-Deklaration
  6. nur bei XSD: Datentypen und Wertebereiche (z. B. Datum, Zahl ≥ 0)
Typische Fallen
  • Ein nicht wohlgeformtes Dokument ist streng genommen gar kein XML-Dokument: Der Parser bricht beim ersten Syntaxfehler ab. Gültigkeitsfehler meldet ein validierender Parser dagegen alle.
  • „Gültig“ bezieht sich immer auf eine bestimmte DTD/XSD. Ohne DTD/XSD kann ein Dokument nur wohlgeformt sein.
  • Falsche Groß-/Kleinschreibung im End-Tag (<name>…</Name>) ist ein Wohlgeformtheitsfehler, kein Gültigkeitsfehler. Ein Element, das die DTD nicht kennt, ist dagegen ein Gültigkeitsfehler – syntaktisch ist es in Ordnung.

DTD (Document Type Definition) Kam vor – 1/9 – W22

Die DTD ist die Grammatik (der Bauplan) eines Dokumenttyps: Sie legt fest, welche Elemente und Attribute vorkommen dürfen, in welcher Reihenfolge und wie oft. Wofür? Damit Sender und Empfänger eine gemeinsame, verbindliche Struktur haben (Schnittstellenvertrag) und eingehende Dokumente automatisch geprüft (validiert) werden können, bevor sie verarbeitet werden. Die DTD kann im Dokument stehen (interne DTD in <!DOCTYPE spielplan [ … ]>) oder – wie oben – in einer externen Datei, auf die die DOCTYPE-Deklaration mit SYSTEM "datei.dtd" verweist; so können viele Dokumente dieselbe DTD nutzen.

  1. DTD in Worte fassen: Für jedes Element notieren, welche Kinder in welcher Reihenfolge und Anzahl erlaubt sind; für jedes Attribut: Pflicht? erlaubte Werte? ID?
  2. Erster Durchgang – Wohlgeformtheit, Zeile für Zeile: passt jedes End-Tag exakt (auch Groß-/Kleinschreibung, Schrägstrich)? Ist alles korrekt verschachtelt und geschlossen? Stehen alle Attributwerte in Anführungszeichen?

Syntax Prüfungskern – 4/9 – W24, S24, W23, S23

JSON (JavaScript Object Notation) ist ein schlankes, textbasiertes Datenaustauschformat. Es ist das Standardformat von REST-APIs und dokumentenorientierten NoSQL-Datenbanken (z. B. MongoDB). Medientyp: application/json, Zeichenkodierung UTF-8. JSON kennt genau sechs Arten von Werten:

TypSchreibweiseBeispiel
Objekt{ "schlüssel": wert, … } – ungeordnete Menge von Schlüssel-Wert-Paaren{"kursNr": 101, "titel": "Rückenfit"}
Array[ wert, wert, … ] – geordnete Liste beliebiger Werte["MO", "MI", "FR"]
Stringin doppelten Anführungszeichen"Rückenfit", "2026-09-07"
Zahlohne Anführungszeichen, Dezimalpunkt, optional mit Exponent12, 45.00, -3.5, 1.2e3
Booleantrue oder false (klein geschrieben)"ausgebucht": false
nullnull – „kein Wert vorhanden“"start": null

Objekte und Arrays lassen sich beliebig verschachteln. Schlüssel sind immer Strings in doppelten Anführungszeichen. Ein Datum hat keinen eigenen Typ – es wird als String geschrieben, üblich im ISO-Format "JJJJ-MM-TT".

Beispiel: Die Tabelle Kurs eines Sportvereins …

    { "kursNr": 101, "titel": "Rückenfit", "trainerin": "Meyer", "plaetze": 12,
      "ausgebucht": false, "beitrag": 45.00, "start": "2026-09-07" },

Typische Syntaxfehler
  • einfache Anführungszeichen ('titel') oder Schlüssel ohne Anführungszeichen (titel: …) – erlaubt ist nur "titel"
  • Komma nach dem letzten Element ([1, 2, 3,]) oder fehlendes Komma zwischen zwei Paaren
  • Dezimalkomma (45,00) statt Dezimalpunkt – das Komma trennt in JSON Elemente!
  • True, FALSE, NULL, undefined – nur true, false, null sind erlaubt
  • Kommentare (//, /* */) gibt es in JSON nicht
  • Zahlen mit führender Null (007) sind ungültig – Postleitzahlen, Telefonnummern und IDs mit führender Null daher als String: "plz": "01067"
  • Anführungszeichen im Text müssen maskiert werden: "titel": "Kurs \"Fit ab 60\""
  • Zahlen in Anführungszeichen ("plaetze": "12") sind zwar gültiges JSON, aber dann ein String – in Prüfungen wird auf passende Datentypen geachtet.

So gehst du vor: Tabellen in JSON überführen Kam vor – 2/9 – W23, S23

  1. Jede Zeile wird ein Objekt {…}, jede Spalte ein Schlüssel (Spaltennamen übernehmen, sofern nichts anderes verlangt ist).
  2. Mehrere Zeilen kommen in ein Array […], meist mit sprechendem Namen: {"kurse": [ … ]}.
  3. Datentyp je Spalte wählen: Zahlen ohne Anführungszeichen, Texte und Datumswerte mit, ja/nein → true/false, leere Zelle → null.
  4. Beziehungen (Fremdschlüssel) abbilden: entweder als Verweis (die ID wird übernommen) oder eingebettet (die zugehörigen Datensätze stehen als Array im übergeordneten Objekt) – siehe unten.
  5. Zum Schluss Klammern zählen und Kommas prüfen: Komma zwischen den Elementen, nie nach dem letzten.

Der umgekehrte Weg (S23 T1 A4cb: JSON-Sensordaten in ein Relationenmodell übernehmen): Jedes wiederkehrende Objekt wird eine Entität/Tabelle, ein eingebettetes Array wird eine eigene Tabelle mit Fremdschlüssel auf das übergeordnete Objekt.

Embedding und Referenz Kam vor – 1/9 – W23

In einer dokumentenorientierten Datenbank (Sammlungen von JSON-Dokumenten statt Tabellen) gibt es zwei Möglichkeiten, eine 1:n-Beziehung abzubilden. Beispiel: Abteilungen eines Sportvereins und ihre Trainingszeiten.

Begriffe Kam vor – 2/9 – S26, S24

  • Schnittstelle / API (Application Programming Interface): festgelegter Zugang, über den ein Programm Funktionen oder Daten eines anderen Programms nutzt – welche Anfragen möglich sind, wie sie aussehen und was zurückkommt.

Sicher und idempotent Hintergrund – 0/9

  • Sicher (safe): Die Methode verändert auf dem Server nichts, sie liest nur. Sicher sind GET, HEAD und OPTIONS.
  • Idempotent: Wird dieselbe Anfrage mehrfach gesendet, ist der Zustand auf dem Server danach derselbe wie nach einmaligem Senden. Idempotent sind alle sicheren Methoden sowie PUT (zweimal „ersetze durch X“ ergibt X) und DELETE (zweimal löschen: weg ist weg – die zweite Antwort darf 404 sein, der Zustand ändert sich nicht mehr).
  • Nicht idempotent: POST – jede Wiederholung kann eine weitere Ressource anlegen. PATCH ist nicht garantiert idempotent: „setze E-Mail auf x“ wäre es, „erhöhe den Zähler um 1“ nicht. Entscheidend ist also, was die konkrete Änderung bewirkt.

Warum das wichtig ist: Bei schlechter Verbindung weiß ein Client oft nicht, ob seine Anfrage angekommen ist. Idempotente Anfragen darf er (oder ein Proxy) gefahrlos wiederholen – bei nicht idempotenten Anfragen kann eine Wiederholung Schaden anrichten.

PUT oder PATCH? Kam vor – 2/9 – S26, S24

Die Ressource /leser/4711 sieht so aus: {"leserNr": 4711, "name": "Tom Berger", "email": "tom@mail.example", "newsletter": false}. Nur die E-Mail-Adresse soll sich ändern:

PUT /v2/leser/4711
Content-Type: application/json

{"leserNr": 4711, "name": "Tom Berger",
 "email": "t.berger@mail.example",
 "newsletter": false}
PATCH /v2/leser/4711
Content-Type: application/json

{"email": "t.berger@mail.example"}

PUT überträgt die vollständige neue Repräsentation und ersetzt die alte. Schickt man bei PUT nur ein Feld, wären die übrigen danach leer bzw. auf Standardwerte gesetzt. PATCH überträgt nur die Änderung.

Endpunkte entwerfen Hintergrund – 0/9

  • Substantive statt Verben, Sammlungen im Plural: /medien, nicht /getMedien. Die Aktion steckt in der HTTP-Methode.
  • Hierarchie für abhängige Ressourcen: /leser/{leserNr}/ausleihen/{ausleihId}.
  • Pfadparameter identifizieren eine bestimmte Ressource (/medien/M-30815). Query-Parameter filtern, sortieren oder teilen eine Ergebnisliste in Seiten auf (/medien?typ=dvd&sort=titel&seite=2) – sie sind meist optional.
  • Kleinbuchstaben, keine Dateiendungen (.json); das Format regeln Accept und Content-Type.
  • Versionierung, meist im Pfad (/v1/…, /v2/…), seltener über einen Header: Bei inkompatiblen Änderungen (Feld umbenannt, Struktur geändert) wird eine neue Version veröffentlicht, die alte bleibt eine Zeit lang parallel erreichbar. So funktionieren bereits ausgelieferte Clients (z. B. nicht aktualisierte Apps) weiter.
  • Dokumentiert werden REST-APIs heute meist mit OpenAPI (früher Swagger).

API-Schlüssel Kam vor – 1/9 – S26

Ein API-Schlüssel (API key) ist eine eindeutige, geheime Zeichenfolge, mit der sich eine Anwendung (nicht eine Person) gegenüber einer API ausweist. Zweck: nur registrierte Clients erhalten Zugriff, Anfragen lassen sich einem Kunden zuordnen (Abrechnung, Statistik), und die Anzahl der Anfragen lässt sich begrenzen (Rate-Limiting, Überschreitung → 429 Too Many Requests). Übertragung immer über HTTPS, besser im Header als in der URL, und nie im öffentlich einsehbaren Quellcode ablegen. Ein API-Schlüssel ersetzt keine Benutzeranmeldung – dafür gibt es Tokens (z. B. OAuth 2.0).

Was ist eine eRechnung? Kam vor – 1/9 – W25

Nach der EU-Richtlinie 2014/55/EU und § 14 UStG ist eine elektronische Rechnung (eRechnung, e-invoice) eine Rechnung, die in einem strukturierten elektronischen Format ausgestellt, übermittelt und empfangen wird und eine automatische und elektronische Verarbeitung ermöglicht. In Deutschland muss das Format der europäischen Norm EN 16931 entsprechen (oder mit ihr kompatibel sein).

Merke Das Hauptziel der eRechnung ist die automatische Verarbeitung: Die Rechnungsdaten werden ohne Abtippen direkt in die Software des Empfängers (Buchhaltung, ERP) übernommen und geprüft. Eine für Menschen lesbare Darstellung ist zweitrangig.
Eine PDF-Rechnung ist deshalb keine eRechnung (sondern eine „sonstige Rechnung“) – ebenso wenig ein Scan oder ein Foto einer Papierrechnung.

Zwei Aspekte einer digitalen Rechnung: Der visuelle Aspekt erlaubt einem Menschen, den Inhalt zu sehen und zu lesen (z. B. als PDF). Der Datenaspekt erlaubt einem Computer, die enthaltenen Informationen strukturiert zu verarbeiten (z. B. als XML mit festgelegten Feldern für Rechnungsnummer, Beträge, Steuersätze). Eine PDF hat nur den visuellen Aspekt, eine XRechnung nur den Datenaspekt, ZUGFeRD beide.

Vorteile: keine manuelle Erfassung, dadurch weniger Fehler und schnellere Bearbeitung und Zahlung; geringere Kosten für Druck, Porto und Erfassung; einfache, durchsuchbare Archivierung; automatische Prüfung (Pflichtangaben, Rechenwerte); Grundlage für digitale Meldeverfahren der Steuerverwaltung. Herausforderungen: Software muss eRechnungen erzeugen, prüfen, anzeigen und revisionssicher im Originalformat archivieren; Abläufe und Stammdaten müssen angepasst werden.

Übertragungswege Hintergrund – 0/9

Das Gesetz schreibt keinen bestimmten Weg vor. Üblich sind:

  • E-Mail mit der XML- bzw. ZUGFeRD-Datei als Anhang (an eine eigens eingerichtete Rechnungsadresse),
  • Upload in ein Portal – z. B. die Rechnungseingangsplattformen von Bund und Ländern (ZRE, OZG-RE) oder ein Lieferantenportal,
  • Peppol: europäisches Netzwerk für den Austausch von Geschäftsdokumenten; Sender und Empfänger sind über zertifizierte Zugangspunkte (Access Points) angebunden, die Zustellung ist sicher und nachweisbar,

Validierung: Entspricht die Rechnung der Spezifikation? Kam vor – 1/9 – W25

Eine eRechnung wird in zwei Stufen geprüft:

  1. Schema-Validierung (XSD von UBL bzw. CII): Struktur, Pflichtelemente, Reihenfolge, Datentypen (Datum, Dezimalzahl, Codes). Sie stellt die formale Korrektheit sicher.
  2. Schematron-Prüfung: Geschäftsregeln der EN 16931 und der XRechnung, die sich mit einem Schema nicht ausdrücken lassen – z. B. „Summe der Positionsnettobeträge = Nettogesamtbetrag“, „Bruttobetrag = Nettobetrag + Umsatzsteuer“, „bei XRechnung ist die Käuferreferenz (Leitweg-ID) anzugeben“.

Beides erledigt der KoSIT-Validator, das offizielle Prüfwerkzeug: frei verfügbar (Open Source), lokal ausführbar und auch in automatisierte Tests einbindbar; er erstellt einen Prüfbericht. Bei der Entwicklung einer Rechnungssoftware sichern außerdem ab: die verbindlichen Anforderungen der Spezifikation konsequent umsetzen, erprobte Bibliotheken nutzen, automatisierte Tests mit den offiziellen Testrechnungen, Testläufe mit Empfängern bzw. deren Portalen (Interoperabilität) und die Validierung als festen Schritt vor jedem Versand.

Datenschutz und Sicherheit Kam vor – 1/9 – W25

  • Online-Prüfseiten: Rechnungen enthalten personenbezogene Daten (Namen, Anschriften, Bankverbindungen) und Geschäftsgeheimnisse (Preise, Mengen, Kundenbeziehungen). Wer eine Rechnung auf eine fremde Website hochlädt, übermittelt diese Daten an Dritte – nach DSGVO braucht das eine Rechtsgrundlage. Deshalb: keine echten Rechnungen hochladen, nur Test- oder anonymisierte Daten; den Anbieter prüfen (Impressum, Sitz bzw. Serverstandort, Datenschutzerklärung, Löschung); bedenken, dass das Ergebnis einer unbekannten Seite falsch oder veraltet sein kann (welche Regeln und welche Version werden geprüft?); im Zweifel den Validator lokal betreiben.
  • Transport: Beim E-Mail-Versand verschlüsselt TLS die Verbindung zwischen den Mailservern (Transportverschlüsselung). TLS ist ein hybrides Verfahren: asymmetrische Verschlüsselung für den sicheren Austausch eines Sitzungsschlüssels, symmetrische Verschlüsselung für die schnelle Übertragung der Daten. Die Transportverschlüsselung schützt nur die einzelnen Teilstrecken; auf den beteiligten Servern liegt die Nachricht unverschlüsselt. Ende-zu-Ende schützen S/MIME oder PGP bzw. die Übermittlung über Peppol oder ein Portal per HTTPS. (Kryptografie im Detail: Block 07.)

Anlage 11 · Fachtext zur eRechnung

E-invoicing in Germany: what businesses need to know

Since 1 January 2025, every business in Germany has to be able to receive electronic invoices from other businesses (B2B). Under the new rules, an e-invoice is an invoice that is issued, transmitted and received in a structured electronic format which complies with the European standard EN 16931 and allows the data to be processed automatically. A PDF file attached to an e-mail is therefore no longer regarded as an e-invoice but as an “other invoice”. Invoices to private consumers (B2C) are not affected by the new rules.

For issuing e-invoices, the law provides transition periods. Until 31 December 2026, businesses may still send paper invoices or invoices in other electronic formats such as PDF; sending a PDF, however, requires the consent of the recipient. During 2027, this option is only available to businesses whose total turnover in the previous year did not exceed EUR 800,000. From 1 January 2028, all businesses must issue e-invoices. Invoices for small amounts of up to EUR 250 and travel tickets are exempt.

Two formats are widely used. XRechnung is a purely XML-based format; it is required by many public authorities, which use a routing ID (“Leitweg-ID”) to forward each invoice to the responsible department. ZUGFeRD is a hybrid format: a PDF/A-3 document that contains the invoice data as an embedded XML file. People can read the PDF, while software processes the XML. If the two parts differ, the XML data prevail.

The law does not prescribe a specific transmission channel. E-invoices can be sent by e-mail, uploaded to a portal, exchanged via an API or delivered through the Peppol network. In any case, they must be stored in their original format.

Selbst verfasster Text auf Grundlage der Rechtslage 2026.
