Klasse und Objekt

Eine Klasse ist der Bauplan (Datentyp) für gleichartige Objekte. Sie legt fest, welche Attribute (Daten, Eigenschaften) und welche Methoden (Operationen, Verhalten) jedes Objekt hat. Ein Objekt (Instanz, Exemplar) ist ein konkretes Exemplar einer Klasse, das zur Laufzeit mit new erzeugt wird. Jedes Objekt hat eigene Attributwerte (seinen Zustand) und eine eigene Identität – zwei Objekte mit gleichen Werten sind trotzdem zwei verschiedene Objekte.

Kapselung und Sichtbarkeiten

Datenkapselung (Geheimnisprinzip, information hiding) bedeutet: Die Attribute eines Objekts sind nach außen verborgen (private). Andere Objekte greifen nur über die öffentlichen Methoden zu. Dadurch entscheidet allein die Klasse, welche Änderungen erlaubt sind – ein Konto lässt sich nur über abheben verringern, und abheben prüft das Limit.

MerkeFaustregel für jedes Klassendiagramm: Attribute - (private), Methoden + (public). Reine Hilfsmethoden, die nur intern gebraucht werden, sind -. Attribute, auf die Unterklassen direkt zugreifen sollen, sind #.
Vorteile der Kapselung: (1) Gültigkeit der Daten – Setter und Methoden prüfen Werte, bevor sie gespeichert werden; (2) Wartbarkeit – die interne Darstellung (z. B. Saldo in Cent statt Euro) kann geändert werden, ohne dass andere Klassen angepasst werden müssen; (3) geringe Kopplung – andere Klassen hängen nur von der öffentlichen Schnittstelle ab; (4) Fehler lassen sich leichter eingrenzen, weil nur die Klasse selbst ihren Zustand ändert.

Getter und Setter

  • Getter lesen ein Attribut: getSaldo() : double, bei boolean üblich isGesperrt() : boolean.
  • Setter ändern ein Attribut: setDispo(dispo : double) : void. Ein guter Setter prüft den Wert und lehnt ungültige Werte ab.
  • Nicht jedes Attribut braucht einen Setter. Werte, die sich nach der Erzeugung nicht ändern dürfen (Kontonummer), werden nur im Konstruktor gesetzt; in Java zusätzlich mit final gekennzeichnet.
  • In IHK-Aufgaben steht oft „Für alle Attribute existieren Get-Methoden“. Dann benutzt du in deinem Code immer die Getter (k.getSaldo()), nie das Attribut direkt (k.saldo).

Konstruktor, Überladen und this

  • Der Konstruktor ist eine besondere Methode mit dem Namen der Klasse und ohne Rückgabetyp. Er wird bei new automatisch aufgerufen und bringt das neue Objekt in einen gültigen Anfangszustand (Attribute setzen, Startwerte, Zähler erhöhen).
  • Schreibt man keinen Konstruktor, gibt es automatisch einen parameterlosen Standardkonstruktor. Sobald man selbst einen Konstruktor schreibt, entfällt er.
  • Überladen: Mehrere Konstruktoren (oder Methoden) mit gleichem Namen, aber unterschiedlicher Parameterliste (Anzahl, Typen oder Reihenfolge). Der Rückgabetyp allein reicht zur Unterscheidung nicht.
  • this verweist auf das aktuelle Objekt:
    1. this.saldo := saldo – unterscheidet das Attribut vom gleichnamigen Parameter,
    2. this(kontoNr, inhaber, 0.0) – ruft einen anderen Konstruktor derselben Klasse auf (muss die erste Anweisung sein) und vermeidet doppelten Code,
    3. bank.registrieren(this) – übergibt das eigene Objekt an ein anderes Objekt (wichtig beim Observer-Muster).

Statische Attribute und Methoden (Klassenattribute, Klassenmethoden)

Ein mit static gekennzeichnetes Attribut gehört zur Klasse, nicht zu einem einzelnen Objekt. Es existiert genau einmal und wird von allen Objekten geteilt. Eine statische Methode wird über den Klassennamen aufgerufen (Konto.getAnzahlKonten()), auch wenn noch kein Objekt existiert. Sie hat kein this und kann deshalb nicht direkt auf Instanzattribute zugreifen.

  • Typische Verwendung: Zähler für erzeugte Objekte, fortlaufende Nummern, Konstanten (static final), Hilfsmethoden (Math.sqrt), Fabrikmethoden und Singleton (OOP-04).
  • UML: statische Elemente werden unterstrichen. Der IHK-Belegsatz erlaubt alternativ die Eigenschaft {static} hinter der Signatur.
Typische Falle bei staticWird ein Attribut, das je Objekt verschieden sein muss, versehentlich static deklariert (z. B. saldo), teilen sich alle Konten einen einzigen Saldo. Umgekehrt zählt ein nicht-statischer Zähler nur im eigenen Objekt und steht bei jedem neuen Objekt wieder auf dem Startwert.

class Konto {
    private static int anzahlKonten = 0;
    private final String kontoNr;
    private String inhaber;
    private double saldo;
    private double dispo;

    public Konto(String kontoNr, String inhaber, double dispo) {
        this.kontoNr = kontoNr;
        this.inhaber = inhaber;
        this.saldo = 0.0;
        this.dispo = 0.0;
        setDispo(dispo);
        anzahlKonten = anzahlKonten + 1;
    }

    public Konto(String kontoNr, String inhaber) {
        this(kontoNr, inhaber, 0.0);
    }

    public void setDispo(double dispo) {
        if (dispo >= 0 && dispo <= 2000) {
            this.dispo = dispo;
        }
    }

    public boolean abheben(double betrag) {
        if (betrag > 0 && saldo - betrag >= -dispo) {
            saldo = saldo - betrag;
            return true;
        }
        return false;
    }

    public static int getAnzahlKonten() {
        return anzahlKonten;
    }

    public double getSaldo() {
        return saldo;
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof Konto && kontoNr.equals(((Konto) o).kontoNr);
    }
}

Referenzen, null, Identität und Gleichheit

Eine Variable vom Typ einer Klasse enthält nicht das Objekt selbst, sondern einen Verweis (Referenz) darauf. Eine Zuweisung k3 := k1 kopiert nur den Verweis: Danach zeigen beide Variablen auf dasselbe Objekt (Aliasing), und eine Änderung über k3 ist auch über k1 sichtbar. null bedeutet „zeigt auf kein Objekt“; ein Methodenaufruf auf null führt zur NullPointerException.

So gehst du vor: Klasse aus Text oder Klassendiagramm umsetzen

  1. Attribute sammeln: Jedes Substantiv mit einem Wert („Fachnummer“, „ob gesperrt“) wird ein Attribut mit passendem Typ (integer, double, string, boolean, eine Klasse oder List<…>). Sichtbarkeit -.
  2. Klassenweite Werte erkennen: „für alle Objekte gemeinsam“, „Anzahl aller …“, „ohne dass ein Objekt existiert“ → static (unterstrichen).
  3. Konstruktoren: Welche Werte müssen beim Erzeugen feststehen? Weitere Varianten mit Standardwerten als überladene Konstruktoren, die per this(…) den vollständigen Konstruktor aufrufen.
  4. Getter und Setter nur dort, wo sie gebraucht werden; Setter prüfen Werte; unveränderliche Werte bekommen keinen Setter.
  5. Fachmethoden: Name als Verb, Parameter mit Typ, Rückgabetyp. Vorbedingungen prüfen (wenn … dann), Zustand ändern, Erfolg melden (boolean) oder ein Objekt bzw. null zurückgeben.
  6. Beziehungen: Ein Attribut, dessen Typ eine andere Klasse ist, wird im Diagramm als (gerichtete) Assoziation zu dieser Klasse gezeichnet.
Typische Fehler
  • Konstruktor mit Rückgabetyp (void Konto(…)) – dann ist es eine normale Methode und kein Konstruktor.
  • saldo := saldo statt this.saldo := saldo: Der Parameter wird sich selbst zugewiesen, das Attribut bleibt unverändert.
  • Attribute + (public) oder Setter ohne Prüfung – die Kapselung ist damit wirkungslos.
  • Statische Methode greift auf Instanzattribute zu (es gibt dort kein this) → Compilerfehler.
  • Objekte mit == statt equals verglichen, insbesondere Strings in Java. Im Pseudocode ist = erlaubt, wenn die Aufgabe es zulässt (S26: Hinweis, dass Strings direkt verglichen werden dürfen).
  • Methode auf einer Variablen aufgerufen, die null sein kann, ohne vorher zu prüfen.
  • Zwei Methoden, die sich nur im Rückgabetyp unterscheiden – das ist kein gültiges Überladen.

Vererbung (Generalisierung und Spezialisierung)

Vererbung ist eine „ist-ein“-Beziehung: Die Unterklasse (abgeleitete Klasse, Subklasse) übernimmt alle Attribute und Methoden der Oberklasse (Basisklasse, Superklasse), kann neue hinzufügen und geerbte Methoden überschreiben. Gemeinsamkeiten stehen nur einmal in der Oberklasse (Generalisierung), Besonderheiten in den Unterklassen (Spezialisierung).

  • Java: class Azubi extends Mitarbeiter – genau eine Oberklasse. UML: durchgezogene Linie mit hohlem Dreieck an der Oberklasse.
  • Private Attribute der Oberklasse werden zwar geerbt, sind in der Unterklasse aber nicht direkt zugreifbar – Zugriff über Getter oder das Attribut # (protected) machen.
  • Prüffrage: „Ist ein X ein Y?“ – Ein Azubi ist ein Mitarbeiter ✓. Ein Motor ist kein Auto, das Auto hat einen Motor → Assoziation bzw. Komposition, keine Vererbung.
  • Vorteile: keine Redundanz, Wiederverwendung, Erweiterbarkeit durch neue Unterklassen, Grundlage für Polymorphie (OOP-03). Nachteile: enge Kopplung (eine Änderung der Oberklasse wirkt auf alle Unterklassen), tiefe Hierarchien sind schwer zu überblicken.

Konstruktoren und super

Konstruktoren werden nicht vererbt. Jeder Konstruktor einer Unterklasse ruft als erste Anweisung einen Konstruktor der Oberklasse auf: ausdrücklich mit super(…) oder – wenn man nichts schreibt – automatisch mit super(). Das automatische super() funktioniert nur, wenn die Oberklasse einen parameterlosen Konstruktor hat. Der Oberklassenteil eines Objekts wird also immer zuerst initialisiert („von oben nach unten“).

class Person {
    private String name;

    public Person(String name) {
        this.name = name;
        System.out.println("Person " + name + " angelegt");
    }
}

class Kunde extends Person {
    private int kundenNr;

    public Kunde(String name, int kundenNr) {
        super(name);                   // muss die erste Anweisung sein
        this.kundenNr = kundenNr;
        System.out.println("Kunde " + kundenNr + " angelegt");
    }
}

class Firmenkunde extends Kunde {
    private String firma;

    public Firmenkunde(String name, int kundenNr, String firma) {
        super(name, kundenNr);
        this.firma = firma;
        System.out.println("Firmenkunde " + firma + " angelegt");
    }
}

Mit super.methode() ruft eine Unterklasse außerdem die Oberklassen-Version einer überschriebenen Methode auf, z. B. rückgabe super.urlaubstage() + 2.

protected und final

  • protected (#): sichtbar in der eigenen Klasse und in allen Unterklassen – für Attribute, die Unterklassen direkt lesen oder setzen sollen.
  • final bei einer Klasse: keine Unterklassen möglich (Beispiel String). Bei einer Methode: darf nicht überschrieben werden. Bei einem Attribut: darf nur einmal zugewiesen werden; static final = Konstante.

Abstrakte Klassen

  • Kennzeichnung: Java abstract; UML: Klassenname kursiv und/oder {abstract}, abstrakte Methoden ebenfalls kursiv bzw. mit {abstract}.
  • Von einer abstrakten Klasse können keine Objekte erzeugt werden (new Mitarbeiter(…) ist verboten). Variablen, Parameter und Listen dürfen aber diesen Typ haben (List<Mitarbeiter>).
  • Sie darf Attribute, Konstruktoren (für die Unterklassen), konkrete und abstrakte Methoden enthalten.
  • Eine abstrakte Methode hat nur eine Signatur, keinen Rumpf. Jede konkrete Unterklasse muss sie implementieren (überschreiben) – sonst ist die Unterklasse selbst abstrakt.
  • Wann? Wenn es einen Oberbegriff gibt, von dem es keine „allgemeinen“ Objekte geben soll (es gibt nur Angestellte, Aushilfen und Azubis, aber keinen „Mitarbeiter an sich“), die Unterklassen aber gemeinsame Attribute und gemeinsamen Code haben.

Interfaces (Schnittstellen)

  • Ein Interface ist ein Vertrag: Jede Klasse, die es implementiert, garantiert die vorgegebenen Methoden. Es enthält nur Methodensignaturen (implizit public abstract) und Konstanten, keine Instanzattribute und keinen Konstruktor. (Seit Java 8 sind default-Methoden möglich – für die Prüfung nicht nötig.)
  • Eine Klasse kann beliebig viele Interfaces implementieren: class Rechnung implements Druckbar, Exportierbar.
  • UML: «interface» über dem Namen; Realisierung (Implementierung) = gestrichelte Linie mit hohlem Dreieck am Interface.
  • Ein Interface beschreibt eine Fähigkeit oder Rolle („kann gedruckt werden“, „kann verglichen werden“, „kann beobachten“), die ganz unterschiedliche, sonst nicht verwandte Klassen haben können.

Keine Mehrfachvererbung von Klassen

In Java und C# kann eine Klasse nur von einer Klasse erben. Grund ist das Diamond-Problem: Erben B und C von A und überschreiben beide die Methode m(), wäre bei einer Klasse D extends B, C unklar, welches m() gilt und ob die Attribute von A einmal oder doppelt vorhanden sind. Interfaces haben dieses Problem nicht, weil sie weder Zustand noch (verpflichtende) Implementierung mitbringen: Die implementierende Klasse schreibt die Methode selbst, es gibt also nur eine Implementierung. Deshalb gilt: eine Oberklasse, beliebig viele Interfaces. (C++ erlaubt Mehrfachvererbung und muss den Konflikt mit zusätzlichen Regeln lösen.)

Redundante Fallunterscheidungen durch Vererbung ersetzen

Ein klassischer Prüfungsfall (S23): Eine Klasse hat ein Attribut typ und mehrere Methoden, die alle mit derselben Fallunterscheidung (wenn typ = … dann …) arbeiten. Jeder neue Typ zwingt dazu, alle diese Methoden zu ändern – vergisst man eine, entsteht ein Fehler. Beispiel aus einer Personalverwaltung:

Methodetyp = "ANGESTELLT"typ = "AUSHILFE"typ = "AZUBI"
gehalt()monatsgehaltstundenlohn * stunden1000 + 100 * lehrjahr
urlaubstage()30028

Jede Unterklasse implementiert nur „ihre Spalte“ der Tabelle. Beispiel Aushilfe:

klasse Aushilfe erbt von Mitarbeiter
  - stundenlohn : double
  - stunden : double

  konstruktor Aushilfe(name : string,
                       stundenlohn : double)
    super(name)
    this.stundenlohn := stundenlohn
    stunden := 0.0
  Ende konstruktor

  methode setStunden(stunden : double) : void
    this.stunden := stunden
  Ende methode

  methode gehalt() : double
    rückgabe stundenlohn * stunden
  Ende methode

  methode urlaubstage() : integer
    rückgabe 0
  Ende methode
Ende klasse

In Java entspricht erbt von dem Schlüsselwort extends, die überschreibenden Methoden werden mit @Override markiert.

So gehst du vor

  1. Jeder Wert des Typ-Attributs wird eine Unterklasse (Name aus dem Fachbegriff: "AZUBI" → Azubi, "ANGESTELLT" → Angestellter).
  2. Die Oberklasse wird abstrakt, das Attribut typ entfällt (auch aus dem Konstruktor).
  3. Was für alle Typen gleich ist (Attribute, Getter, gleiche Methoden), bleibt nur in der Oberklasse – nicht in den Unterklassen wiederholen.
  4. Jede Methode mit Fallunterscheidung wird in der Oberklasse abstrakt (kursiv bzw. {abstract}) und in jeder Unterklasse mit genau ihrem Zweig implementiert.
  5. Nur für einen Typ benötigte Attribute (lehrjahr, stundenlohn) wandern in die passende Unterklasse.
  6. Haben nur einige Typen eine Fähigkeit, wird sie als Interface modelliert, das nur diese Unterklassen realisieren.
  7. Wer entscheidet beim Erzeugen, welche Unterklasse gebraucht wird? → Fabrikmethode (OOP-04).
  8. Pfeile prüfen: Dreieck immer an der Oberklasse bzw. am Interface.

Vorteil des neuen Entwurfs: Ein neuer Typ ist eine neue Unterklasse; bestehende, getestete Klassen bleiben unverändert (Open-Closed-Prinzip: offen für Erweiterung, geschlossen für Änderung). Keine vergessenen Zweige, kürzere und verständlichere Methoden.

Typische Fehler
  • Dreieck an der Unterklasse statt an der Oberklasse; Realisierung durchgezogen statt gestrichelt.
  • Geerbte Attribute in den Unterklassen noch einmal eintragen.
  • Abstrakte Methode in einer Unterklasse vergessen – dann ist sie nicht instanziierbar.
  • Das Attribut typ im neuen Entwurf stehen lassen.
  • Im Unterklassen-Konstruktor super(…) vergessen, obwohl die Oberklasse keinen parameterlosen Konstruktor hat.
  • Vererbung nur „zur Code-Wiederverwendung“ einsetzen, obwohl keine ist-ein-Beziehung besteht.
  • class D extends B, C – in Java nicht möglich.
So wird es in der Prüfung gefragt

Gefordert: Polymorphie erläutern, Klassendiagramm mit abstrakter Oberklasse ohne Typ-Attribut und mit statischer Fabrikmethode zeichnen, Fabrikmethode und überschreibende Methoden in Pseudocode schreiben.

Polymorphie (Vielgestaltigkeit)

Definition (prüfungsreif)Polymorphie bedeutet, dass eine Variable vom Typ einer Oberklasse oder eines Interfaces auf Objekte verschiedener Unterklassen verweisen kann und derselbe Methodenaufruf je nach tatsächlichem Objekt unterschiedliches Verhalten auslöst. Möglich wird das durch das Überschreiben von Methoden: Welche Implementierung ausgeführt wird, entscheidet sich erst zur Laufzeit anhand des Objekts (dynamische oder späte Bindung). Der aufrufende Code muss die konkreten Unterklassen nicht kennen und braucht keine Fallunterscheidungen.

Beispiel Stadtbibliothek: Die abstrakte Klasse Medium hat die abstrakte Methode leihfrist() : integer. Buch liefert 28 Tage, DVD 7 Tage, Zeitschrift 14 Tage. Eine Methode, die alle Medien einer Ausleihe durchläuft, ruft einfach m.leihfrist() auf – jedes Objekt antwortet mit seiner eigenen Implementierung:

methode laengsteFrist(medien : List<Medium>)
        : integer
  max : integer := 0
  zähle i von 0 bis medien.size() - 1
    m : Medium := medien.get(i)
    frist : integer := m.leihfrist()
    // welches leihfrist()? Das Objekt
    // entscheidet (dynamische Bindung)
    wenn frist > max dann
      max := frist
    Ende wenn
  Ende zähle
  rückgabe max
Ende methode

Kommt später eine neue Medienart hinzu (z. B. Hoerbuch mit 21 Tagen), wird nur eine neue Unterklasse geschrieben – die Methode laengsteFrist bleibt unverändert.

Statischer und dynamischer Typ

Bei Medium m := new DVD("Metropolis") ist Medium der statische Typ (deklarierter Typ der Variablen) und DVD der dynamische Typ (Klasse des Objekts, auf das m gerade zeigt).

Merke: zwei Fragen, zwei Typen
  1. Ist der Aufruf erlaubt? – entscheidet der Compiler mit dem statischen Typ. Über m sind nur Methoden aufrufbar, die Medium kennt. Eine Methode, die nur DVD hat (z. B. laufzeitMinuten()), ist über m nicht aufrufbar.
  2. Welche überschriebene Implementierung läuft? – entscheidet die Laufzeitumgebung mit dem dynamischen Typ: m.leihfrist() führt DVD.leihfrist() aus.
  3. Ruft eine geerbte Methode intern eine überschriebene Methode auf (this.leihfrist()), gilt ebenfalls der dynamische Typ des Objekts.

Eine Klasse Etikettendrucker hat zwei überladene Methoden drucke(m : Medium) (druckt „Medium“) und drucke(b : Buch) (druckt „Buch“).

Medium m = new Buch("Faust");
Buch b = new Buch("Woyzeck");

drucker.drucke(b);   // Ausgabe: Buch

Obwohl m auf ein Buch zeigt, wird drucke(Medium) gewählt, denn welche überladene Variante passt, entscheidet der Compiler mit den statischen Typen. Dynamisch gebunden wird nur beim Überschreiben.

Falle: Unterklasse überlädt statt zu überschreibenSchreibt eine Unterklasse eine Methode mit gleichem Namen, aber anderer Parameterliste (leihfrist(verlaengert : boolean)), ist das kein Überschreiben. Die geerbte leihfrist() bleibt unverändert und wird weiterhin aufgerufen. @Override würde diesen Fehler beim Übersetzen melden.

Upcast, Downcast und instanceof

  • Upcast (Unterklasse → Oberklasse) geschieht automatisch und ist immer sicher: Medium m := new DVD(…).
  • Downcast (Oberklasse → Unterklasse) muss ausdrücklich geschrieben werden: DVD d = (DVD) m;. Der Compiler erlaubt ihn, wenn die Typen verwandt sind. Zeigt m zur Laufzeit aber nicht auf eine DVD, entsteht eine ClassCastException.
  • Deshalb vorher mit instanceof prüfen: if (m instanceof DVD) { DVD d = (DVD) m; … } (ab Java 16 kürzer: if (m instanceof DVD d) { … }). In Pseudocode: wenn m ist DVD dann.
  • Viele instanceof-Abfragen sind ein Zeichen für schlechten Entwurf – meist gehört das Verhalten als überschriebene Methode in die Unterklassen.

Generics: generische Klassen und Methoden

Eine generische Klasse hat einen oder mehrere Typparameter (Platzhalter für einen Datentyp), z. B. class Warteschlange<T>. Erst beim Verwenden wird der konkrete Typ festgelegt: Warteschlange<Patient>, Warteschlange<String>. Die bekanntesten generischen Klassen sind die Collections: List<T>, Map<K, V>.

Pseudocode

klasse Warteschlange<T>
  - elemente : List<T>

  konstruktor Warteschlange()
    elemente := new List<T>()
  Ende konstruktor

  methode einreihen(e : T) : void
    elemente.add(e)
  Ende methode

  methode naechster() : T
    wenn elemente.size() = 0 dann
      rückgabe null
    Ende wenn
    erster : T := elemente.get(0)
    elemente.remove(erster)
    rückgabe erster
  Ende methode
Ende klasse

Verwendung (Java)

Warteschlange<Patient> praxis = new Warteschlange<>();
praxis.einreihen(new Patient("Ahmadi"));
praxis.einreihen(new Patient("Brandt"));
Patient naechster = praxis.naechster();   // kein Cast nötig
// praxis.einreihen("Brandt");            // Compilerfehler: String ist kein Patient

Vorteile gegenüber einer Klasse, die Elemente vom Typ Object speichert:

  • Typsicherheit beim Übersetzen: In eine Warteschlange<Patient> lässt der Compiler nur Patient-Objekte hinein. Mit Object passt alles hinein, ein falscher Typ fällt erst zur Laufzeit als ClassCastException auf.
  • Keine Typumwandlungen (Casts) beim Herausholen – der Rückgabetyp ist bereits Patient.
  • Wiederverwendbarkeit: Eine einzige Implementierung funktioniert für beliebige Typen, ohne Code zu kopieren (PatientenWarteschlange, AuftragsWarteschlange …).
  • Lesbarkeit: Am Typ sieht man sofort, was gespeichert wird.

Weitere Formen: generische Methode mit eigenem Typparameter (<T> T letztes(List<T> liste)), beschränkter Typparameter <T extends Medium> – dann dürfen auf T die Methoden von Medium aufgerufen werden. Typparameter stehen nur für Referenztypen: List<Integer>, nicht List<int>.

Funktionsobjekte: eine Vergleichsfunktion als Parameter

Ein generischer Algorithmus (Sortieren, Minimum, „ist die Liste sortiert?“) weiß nicht, wie zwei Objekte vom Typ T zu vergleichen sind. Deshalb bekommt er ein Objekt mit einer Vergleichsmethode übergeben – in Java das Interface Comparator<T> mit compare(a, b):

  • Ergebnis negativ: a kommt vor b (a ist „kleiner“), 0: gleichwertig, positiv: a kommt nach b.
  • Für jedes Kriterium gibt es eine eigene Klasse (oder in Java einen Lambda-Ausdruck). Der Algorithmus ruft nur v.compare(a, b) auf – das ist wieder Polymorphie (und das Strategie-Muster, OOP-05).
// true, wenn die Liste nach dem Kriterium v
// aufsteigend sortiert ist

                          v : Comparator<T>) : boolean
  zähle i von 1 bis liste.size() - 1
    wenn v.compare(liste.get(i - 1), liste.get(i)) > 0 dann
      rückgabe false
    Ende wenn
  Ende zähle
  rückgabe true
Ende methode

Verwendung in Java (Vergleichsfunktion als Lambda-Ausdruck)

List<Buch> buecher = new ArrayList<>();
buecher.add(new Buch("Faust", 1808));
buecher.add(new Buch("Woyzeck", 1879));

  • Methode der Unterklasse über eine Oberklassen-Variable aufrufen → Compilerfehler.
  • Überladen und Überschreiben verwechselt; vergessen, dass Überladen statisch gebunden wird.
  • Downcast ohne instanceof-Prüfung.
  • Rückgabewert der Vergleichsfunktion falsch gedeutet (> 0 heißt „a gehört hinter b“).

Was ist ein Entwurfsmuster?

Ein Entwurfsmuster (Design Pattern) ist eine bewährte, wiederverwendbare Lösungsvorlage für ein wiederkehrendes Entwurfsproblem der Softwareentwicklung. Es ist kein fertiger Code und keine Bibliothek, sondern eine Idee mit typischer Struktur (beteiligte Klassen, Interfaces und ihre Beziehungen), die auf die konkrete Situation übertragen wird. Bekannt wurde das Konzept durch den Katalog der „Gang of Four“ (Gamma, Helm, Johnson, Vlissides, 1994) mit 23 Mustern. Jedes Muster wird beschrieben durch Name, Problem, Lösung und Konsequenzen (Vor- und Nachteile).

VorteilErläuterung
Bewährte LösungenDie Lösung wurde vielfach erprobt; typische Entwurfsfehler werden vermieden, die Qualität steigt.
Gemeinsames Vokabular„Hier nehmen wir einen Observer“ ersetzt eine lange Beschreibung – das erleichtert Kommunikation im Team und Dokumentation.
Wartbarkeit und ErweiterbarkeitMuster entkoppeln Klassen (z. B. kennt das Subjekt nur ein Interface). Erweiterungen sind möglich, ohne bestehenden Code zu ändern.
Wiederverwendbarkeit, ZeitersparnisDer Entwurf muss nicht neu erfunden werden; Lösungen lassen sich auf andere Projekte übertragen.
VerständlichkeitWer das Muster kennt, versteht fremden Code schneller; neue Teammitglieder arbeiten sich leichter ein.

Nachteile: zusätzliche Klassen und Indirektion (mehr Komplexität), Gefahr des „Overengineering“ (Muster ohne echtes Problem), Einarbeitungsaufwand, falsch gewählte Muster erschweren die Wartung.

Singleton

Zweck: Von einer Klasse darf es höchstens ein Objekt geben, und alle Programmteile sollen über einen globalen Zugriffspunkt genau dieses Objekt erhalten. Typische Einsätze: zentrales Protokoll (Logger), Konfiguration, Verbindungspool, Druckwarteschlange.

Aufbau (drei Bausteine):

  1. ein privates statisches Attribut, das die einzige Instanz speichert (anfangs null),
  2. ein privater Konstruktor – von außen ist kein new möglich,
  3. eine öffentliche statische Methode getInstance(), die beim ersten Aufruf das Objekt erzeugt („lazy“) und danach immer dasselbe Objekt zurückgibt.
class Protokoll {
    private static Protokoll instanz = null;

    private Protokoll() {
        // z. B. Protokolldatei öffnen
    }

    public static synchronized Protokoll getInstance() {
        if (instanz == null) {
            instanz = new Protokoll();
        }
        return instanz;
    }

    public void schreibe(String text) {
        System.out.println("[LOG] " + text);
    }
}

Aufruf überall im Programm: Protokoll.getInstance().schreibe("Start"). Protokoll.getInstance() == Protokoll.getInstance() liefert true.

Thread-Sicherheit: Rufen zwei Threads getInstance() gleichzeitig zum ersten Mal auf, können beide instanz = null sehen und je ein Objekt erzeugen – dann gibt es zwei. Abhilfe: die Methode synchronized deklarieren (nur ein Thread gleichzeitig), das Objekt schon beim Laden der Klasse erzeugen (private static final Protokoll INSTANZ = new Protokoll();, „eager“) oder in Java ein enum mit genau einem Wert verwenden.

Nachteile: globaler Zustand und versteckte Abhängigkeiten (man sieht einer Methode nicht an, dass sie das Singleton benutzt), schlecht testbar (das Objekt lässt sich nicht durch eine Testattrappe ersetzen), Probleme bei Nebenläufigkeit, die Klasse kümmert sich zusätzlich um ihre eigene Erzeugung.

Fabrikmethode (Factory Method) und statische Fabrikmethode

Problem: An vielen Stellen im Code steht eine Fallunterscheidung, die je nach Parameter eine andere konkrete Klasse mit new erzeugt. Kommt eine Klasse hinzu, müssen alle diese Stellen geändert werden, und der aufrufende Code hängt von allen konkreten Klassen ab.

Lösung (statische Fabrikmethode, wie in S23): Eine einzige – meist statische – Methode in der Oberklasse oder in einer eigenen Fabrikklasse entscheidet anhand eines Parameters, welches Objekt erzeugt wird, und gibt es mit dem Typ der Oberklasse bzw. des Interfaces zurück. Der aufrufende Code kennt nur noch die Abstraktion.

Beispiel: Berichte sollen als CSV, JSON oder XML exportiert werden.

methode erzeugeExporter(format : string) : Exporter  {static}
  wenn format = "CSV" dann
    rückgabe new CsvExporter()
  sonst wenn format = "JSON" dann
    rückgabe new JsonExporter()
  sonst wenn format = "XML" dann
    rückgabe new XmlExporter()
  Ende wenn
  rückgabe null      // unbekanntes Format
Ende methode

// Verwendung – keine Fallunterscheidung mehr:
e : Exporter := Exporter.erzeugeExporter(wahl)
e.exportiere(bericht)

Vorteile: Die Erzeugungslogik steht an einer Stelle (eine neue Klasse = eine Änderung in der Fabrik), der aufrufende Code ist unabhängig von den konkreten Klassen (lose Kopplung), redundante Fallunterscheidungen verschwinden, die Fabrik kann Parameter prüfen und Standardwerte setzen.

Fabrikmethode im Sinne der Gang of Four: Statt einer statischen Methode deklariert eine abstrakte „Erzeuger“-Klasse eine abstrakte Methode erzeugeProdukt(); jede Unterklasse des Erzeugers überschreibt sie und entscheidet so, welches konkrete Produkt entsteht. Die Abstrakte Fabrik erweitert die Idee auf ganze Familien zusammengehöriger Objekte (z. B. alle Bedienelemente im hellen oder dunklen Design). In der Prüfung genügt meist die statische Variante.

Builder (Erbauer) – kurz

Problem: Ein Objekt hat viele, teils optionale Angaben. Konstruktoren mit vielen Parametern sind unlesbar (new Reise("Rom", null, true, false, 2, null)) oder man braucht unzählige überladene Konstruktoren. Lösung: Eine eigene Builder-Klasse sammelt die Angaben Schritt für Schritt über sprechende Methoden und erzeugt mit build() das fertige, vollständig geprüfte Objekt.

Reise r = new Reise.Builder("Rom")      // Pflichtangabe
        .hotel("Albergo Sole")          // optionale Angaben
        .personen(2)
        .build();                       // prüft und erzeugt das Objekt
Typische Fehler
  • Singleton mit public-Konstruktor oder nicht statischem getInstance() (dann bräuchte man schon ein Objekt, um das Objekt zu bekommen).
  • getInstance() erzeugt bei jedem Aufruf ein neues Objekt (Prüfung auf null vergessen).
  • Fabrikmethode gibt den konkreten Typ zurück (: CsvExporter) statt der Oberklasse – dann hängt der Aufrufer wieder von der konkreten Klasse ab.
  • Statische Fabrikmethode im Klassendiagramm nicht als statisch gekennzeichnet.
  • Kategorien verwechselt: Observer und Strategie sind Verhaltensmuster, Adapter, Fassade und Decorator Strukturmuster.

Observer (Beobachter)

Problem: Ein Objekt ändert seinen Zustand, und beliebig viele andere Objekte sollen darüber automatisch informiert werden – ohne dass das geänderte Objekt deren konkrete Klassen kennen muss (1:n-Abhängigkeit, lose Kopplung). Signalwörter in der Aufgabe: „sobald sich … ändert, sollen alle Anzeigen aktualisiert werden“, „weitere Anzeigen sollen später hinzukommen“, „App, Display und Verwaltung zeigen denselben Wert“.

Vorteile des Observer-Musters: lose Kopplung (das Subjekt kennt nur das Interface), beliebig viele Beobachter zur Laufzeit an- und abmeldbar, neue Beobachter-Klassen ohne Änderung des Subjekts (Erweiterbarkeit), kein ständiges Abfragen (Polling). Nachteile: Reihenfolge der Benachrichtigung nicht festgelegt, Kaskaden von Aktualisierungen, vergessenes Abmelden hält Objekte im Speicher, Ablauf schwerer nachvollziehbar.

Muster wählen und begründen – so formulierst du (Beispiel Fußball-Liveticker) „Geeignet ist das Observer-Muster. Der Spielstand ist das Subjekt; die App, die Stadionanzeige und der Liveticker sind Beobachter, die sich beim Spielstand anmelden. Ändert sich der Spielstand, ruft das Subjekt notifyObservers() auf, das bei allen angemeldeten Beobachtern update() aufruft. Dadurch werden alle Anzeigen automatisch und gleichzeitig aktualisiert. Weil das Subjekt nur das Observer-Interface kennt, können später weitere Anzeigen ergänzt werden, ohne die Klasse Spielstand zu ändern (lose Kopplung).“
Aufbau: Muster nennen → Rollen zuordnen → Ablauf in einem Satz → Vorteil für genau diese Situation.

Strategie (Strategy)

Problem: Für eine Aufgabe gibt es mehrere Verfahren (Algorithmen), die austauschbar sein sollen – auch zur Laufzeit – ohne dass die nutzende Klasse lange wenn … sonst wenn …-Ketten enthält. Lösung: Jedes Verfahren wird in eine eigene Klasse gekapselt, die ein gemeinsames Interface realisiert. Die nutzende Klasse (Kontext) hat ein Attribut vom Typ des Interfaces und delegiert die Arbeit an das gerade eingesetzte Strategie-Objekt.

Route r1 = nav.planeRoute("Kiel", "Lübeck");
nav.setStrategie(new Fahrradroute());   // Wechsel zur Laufzeit

Strategie statt Unterklassen des Kontexts: Das Verfahren kann zur Laufzeit gewechselt werden; es entstehen keine Unterklassen für jede Kombination (Navigation für Auto mit schnellster Route, Navigation für Fahrrad …); jedes Verfahren ist einzeln test- und wiederverwendbar; neue Verfahren ändern den Kontext nicht. Das Prinzip dahinter: Komposition statt Vererbung. (Ähnlich aufgebaut ist das Zustandsmuster; dort wechselt das Objekt sein Verhalten aber selbst, je nach Zustand.)

MVC (Model-View-Controller)

Architekturmuster für Anwendungen mit Benutzeroberfläche. Es trennt die Anwendung in drei Teile mit klaren Zuständigkeiten:

  • Model: Daten und Geschäftslogik (z. B. Ausleihen, Regeln, Datenbankzugriff); unabhängig von der Darstellung. Es benachrichtigt die Views bei Änderungen (Observer).
  • View: Darstellung der Daten des Models (Seite, Formular, Diagramm). Mehrere Views auf dasselbe Model sind möglich. Eingaben des Benutzers gibt sie an den Controller weiter.
  • Controller: Steuerung – nimmt Benutzereingaben entgegen, prüft sie, ruft passende Methoden des Models auf und wählt ggf. die anzuzeigende View.

Vorteile: Trennung der Zuständigkeiten, Oberfläche austauschbar (Web, App) bei gleichem Model, mehrere Ansichten derselben Daten, parallele Entwicklung im Team, Model ohne Oberfläche testbar.

Adapter

Problem: Eine vorhandene Klasse (Fremdbibliothek, Altsystem) bietet die benötigte Funktion, aber mit einer anderen Schnittstelle als erwartet, und sie darf oder kann nicht geändert werden. Lösung: Eine Adapter-Klasse realisiert die erwartete Schnittstelle und leitet jeden Aufruf – übersetzt – an das vorhandene Objekt weiter. Beispiel: Die Kühlhaus-Software erwartet Temperaturquelle.getCelsius(), ein neu gekaufter Sensor liefert über seine Bibliothek nur readFahrenheit().

Fassade (Facade)

Problem: Ein Teilsystem besteht aus vielen Klassen, die in einer bestimmten Reihenfolge benutzt werden müssen. Jeder Nutzer müsste alle kennen. Lösung: Eine Fassadenklasse bietet eine einfache, vereinheitlichte Schnittstelle und ruft intern die Klassen des Teilsystems auf. Beispiel: Ein Reiseportal ruft nur ReiseFassade.bucheReise(kunde, angebot) auf; die Fassade reserviert Flug und Hotel, zieht die Zahlung ein und verschickt die Bestätigung.

Abgrenzung: Ein Adapter macht eine vorhandene Schnittstelle passend zu einer erwarteten. Eine Fassade vereinfacht viele Schnittstellen zu einer neuen, einfacheren.

Decorator (Dekorierer)

Problem: Objekte sollen zur Laufzeit beliebig kombinierbare Zusatzfunktionen erhalten. Eine Unterklasse für jede Kombination würde zur „Klassenexplosion“ führen. Lösung: Ein Decorator realisiert dieselbe Schnittstelle wie das Objekt, das er „umhüllt“, hält eine Referenz darauf, leitet Aufrufe weiter und ergänzt eigenes Verhalten. Decorator lassen sich beliebig verschachteln. Beispiel Café: new Sirup(new Milch(new Kaffee())) – preis() ergibt 2,50 + 0,30 + 0,50 = 3,30 €. Bekanntes Java-Beispiel: new BufferedReader(new FileReader("daten.txt")).

    private int nummer;

    public Etikett(String empfaenger, double gewicht) {
        this.nummer = naechsteNr;
        naechsteNr = naechsteNr + 1;
        this.empfaenger = empfaenger;
        this.gewicht = 1.0;
        setGewicht(gewicht);
    }

    public Etikett(String empfaenger) {
        this(empfaenger, 1.0);
    }

    public void setGewicht(double gewicht) {
        if (gewicht > 0 && gewicht <= 31.5) {
            this.gewicht = gewicht;
        }
    }

    public int getNummer() {
        return nummer;
    }

    public static int getAnzahl() {
        return naechsteNr - 1000;
    }

    @Override
    public boolean equals(Object o) {
        if (!(o instanceof Etikett)) {
            return false;
        }
        Etikett e = (Etikett) o;
        return empfaenger.equals(e.empfaenger) && gewicht == e.gewicht;
    }

    @Override
    public int hashCode() {
        return empfaenger.hashCode() + Double.hashCode(gewicht);
    }

Anlage 12 · Sendungsverfolgung

Jede Sendung hat einen Sendungsstatus (z. B. „Im Sortierzentrum“, „In Zustellung“, „In Paketstation eingelegt“). Sobald sich der Status ändert, sollen alle Anzeigen, die diese Sendung verfolgen, sofort aktualisiert werden: die Kunden-App des Empfängers und die Anzeige in der Halle, in der die Sendung bearbeitet wird. Später sollen weitere Anzeigen (z. B. das Kundenportal im Web) hinzukommen, ohne dass die Klasse Sendungsstatus geändert werden muss.

Für die Umsetzung wird das Observer-Muster in der Pull-Variante verwendet: Ein Observer erhält mit update() nur die Nachricht, dass sich etwas geändert hat, und holt sich den neuen Status selbst beim Subject.

Ablaufbeschreibung:

  1. Ein Client erzeugt ein Objekt status der Klasse Sendungsstatus für die Sendung KT-4711.
  2. Der Client erzeugt ein Objekt app der Klasse KundenApp und übergibt status an den Konstruktor. Im Konstruktor meldet sich app mit addObserver(this) bei status an.
  3. Ebenso erzeugt der Client ein Objekt halle der Klasse Hallenanzeige (Halle 3), das sich im Konstruktor bei status anmeldet.
  4. Der Client ruft setStatus("In Zustellung") bei status auf.
  5. Die Methode setStatus speichert den neuen Status und ruft danach die eigene Methode notifyObservers() auf.
  6. notifyObservers() ruft bei allen angemeldeten Observern – in der Reihenfolge der Anmeldung – die Methode update() auf.
  7. In update() holt sich der Observer mit getStatus() den neuen Status bei status, speichert ihn und ruft danach seine eigene Methode anzeigen() auf.
  8. Wenn alle Observer benachrichtigt sind, kehrt die Kontrolle über notifyObservers und setStatus zum Client zurück.
